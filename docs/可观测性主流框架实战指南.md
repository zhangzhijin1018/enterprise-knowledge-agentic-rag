## 1. 可观测性四大支柱

### 1.1 日志（Logs）

**定义**：离散的事件记录，记录"发生了什么"

```
┌─────────────────────────────────────────────────────────────────┐
│                        日志示意图                                 │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  普通日志（文本格式）：                                           │
│  [2024-01-15 14:30:00] INFO  意图识别完成                       │
│                                                                  │
│  问题：                                                          │
│  - 难以搜索：如何搜索"意图识别完成"？                          │
│  - 难以过滤：如何只看某个 trace_id 的日志？                     │
│  - 难以聚合：如何计算平均耗时？                                  │
│                                                                  │
│  结构化日志（JSON 格式）：                                        │
│  {                                                              │
│      "timestamp": "2024-01-15T14:30:00.000Z",                   │
│      "level": "INFO",                                           │
│      "event": "intent_detected",                                 │
│      "trace_id": "tr_abc123",                                   │
│      "intent_type": "analytics",                                  │
│      "confidence": 0.92,                                         │
│      "duration_ms": 45                                           │
│  }                                                              │
│                                                                  │
│  优势：                                                          │
│  - 可搜索：event = "intent_detected"                             │
│  - 可过滤：trace_id = "tr_abc123"                                │
│  - 可聚合：avg(duration_ms)                                      │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### 1.3 指标（Metrics）

**定义**：数值型的测量值，通常随时间聚合

```
┌─────────────────────────────────────────────────────────────────┐
│                    三大指标类型                                    │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  1. Counter（计数器）                                            │
│  ─────────────────────────────────────                          │
│  特点：只能递增，不能减少                                         │
│  用途：请求数、错误数、Token 消耗                                 │
│                                                                  │
│  示例：                                                           │
│  requests_total{endpoint="/chat"} = 12345                        │
│  errors_total{type="timeout"} = 23                               │
│                                                                  │
│  趋势图（只增不减）：                                             │
│  │                                                      ↑       │
│  │                         ╱                                   │       │
│  │                       ╱                                     │       │
│  │                     ╱                                       │       │
│  │                   ╱                                         │       │
│  │────────────────╱──────────────────────────────►               │       │
│                                                                  │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  2. Gauge（仪表）                                                │
│  ─────────────────────────────────────                          │
│  特点：可增可减                                                   │
│  用途：当前连接数、队列长度                                        │
│                                                                  │
│  示例：                                                           │
│  active_connections = 42                                         │
│  queue_length{queue="high"} = 15                                  │
│                                                                  │
│  趋势图（可上可下）：                                             │
│  │     ╭───────╮                                                │
│  │ ───╯         ╰─────╮                                        │
│  │                   ╰──────────────►                          │
│                                                                  │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  3. Histogram（直方图）                                          │
│  ─────────────────────────────────────                          │
│  特点：记录分布，统计百分位数                                      │
│  用途：延迟分布                                                   │
│                                                                  │
│  示例：                                                           │
│  request_duration_seconds_bucket{le="0.1"} = 1000               │
│  request_duration_seconds_bucket{le="0.5"} = 5000               │
│  request_duration_seconds_bucket{le="1.0"} = 8000               │
│                                                                  │
│  分布图：                                                         │
│  │                              ████                            │
│  │                          ████████████████                   │
│  │                      ████████████████████████████            │
│  │██████████                                           ████     │
│  │───────────────────────────────────────────────────────────│  │
│  │ 0ms   100ms  200ms  500ms  1s     延迟                     │
│                                                                  │
│  可计算：P50(中位数)、P90、P99                                   │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### 1.4 审计（Audit）

**定义**：记录安全和合规相关的事件

```
┌─────────────────────────────────────────────────────────────────┐
│                    审计事件类型                                    │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  1. Agent 执行事件                                                │
│  ─────────────────────────────────────                          │
│  • AGENT_REQUEST：收到用户请求                                    │
│  • AGENT_RESPONSE：返回响应                                       │
│  • AGENT_ERROR：执行错误                                         │
│                                                                  │
│  2. 工具调用事件                                                  │
│  ─────────────────────────────────────                          │
│  • TOOL_INVOCATION：工具被调用                                    │
│  • TOOL_RESULT：工具返回结果                                      │
│  • TOOL_ERROR：工具执行错误                                       │
│                                                                  │
│  3. 数据访问事件                                                  │
│  ─────────────────────────────────────                          │
│  • DATA_RETRIEVAL：文档检索                                      │
│  • DATA_QUERY：SQL 查询                                          │
│  • DATA_EXPORT：数据导出                                          │
│                                                                  │
│  4. 高风险操作                                                    │
│  ─────────────────────────────────────                          │
│  • REVIEW_REQUEST：人工复核请求                                    │
│  • REVIEW_APPROVE：复核通过                                      │
│  • REVIEW_REJECT：复核拒绝                                        │
│                                                                  │
│  5. 安全事件                                                      │
│  ─────────────────────────────────────                          │
│  • AUTH_SUCCESS：认证成功                                         │
│  • AUTH_FAILURE：认证失败                                         │
│  • PERMISSION_DENIED：权限拒绝                                   │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

## 2. 为什么选择这些主流框架

### 2.1 框架选型对比

| 场景 | 自研方案 | 主流框架 | 推荐方案 |
|------|----------|----------|----------|
| **日志** | 手写 Formatter | structlog | ✅ structlog |
| **追踪** | 自定义 Span | OpenTelemetry | ✅ OpenTelemetry |
| **指标** | 手写 Histogram | prometheus_client | ✅ prometheus_client |
| **审计** | 自研 | 自研 + 数据库 | ✅ 自研 + DB |

### 2.2 structlog vs 自研

```
┌─────────────────────────────────────────────────────────────────┐
│                  structlog vs 自研对比                           │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  自研方案问题：                                                   │
│  ─────────────────────────────────────                          │
│  1. 需要手写 Formatter、Filter、LogRecord                        │
│  2. 上下文传递需要自己实现 contextvars                           │
│  3. JSON 格式化需要手写 json.dumps                               │
│  4. 生产环境 JSON vs 开发环境彩色需要自己切换                     │
│  5. 第三方库日志桥接需要额外工作                                  │
│                                                                  │
│  structlog 优势：                                                 │
│  ─────────────────────────────────────                          │
│  1. 声明式配置，几行代码搞定                                     │
│  2. 内置 JSON 输出、彩色控制台                                    │
│  3. 自动处理上下文传递                                           │
│  4. 与标准 logging 完全兼容                                      │
│  5. 社区活跃，生产验证                                           │
│                                                                  │
│  代码对比：                                                       │
│  ─────────────────────────────────────                          │
│                                                                  │
│  # 自研方案（80行）                                              │
│  class MyFormatter(logging.Formatter):                            │
│      def format(self, record):                                   │
│          log_data = {                                            │
│              "timestamp": datetime.now().isoformat(),            │
│              "level": record.levelname,                          │
│              "message": record.getMessage(),                      │
│          }                                                        │
│          trace_id = get_trace_id()                               │
│          if trace_id:                                            │
│              log_data["trace_id"] = trace_id                    │
│          return json.dumps(log_data)                              │
│                                                                  │
│  # structlog 方案（5行）                                          │
│  structlog.configure(                                            │
│      processors=[add_trace_context, JSONRenderer()],           │
│  )                                                               │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### 3.2 数据流详解

```
┌─────────────────────────────────────────────────────────────────────┐
│                          数据流详解                                  │
├─────────────────────────────────────────────────────────────────────┤
│                                                                      │
│  1. 日志数据流                                                      │
│  ─────────────────────────────────────                             │
│                                                                      │
│  logger.info("意图识别完成", intent_type="rag")                     │
│         │                                                           │
│         ▼                                                           │
│  structlog Processor Chain                                          │
│         │                                                           │
│         ├── add_trace_context  → 添加 trace_id, run_id             │
│         ├── rename_event_key   → event → message                   │
│         ├── add_timestamp       → 添加 ISO 时间戳                    │
│         └── JSONRenderer        → 输出 JSON                         │
│         │                                                           │
│         ▼                                                           │
│  {"timestamp":"...", "level":"INFO", "message":"意图识别完成",      │
│   "trace_id":"tr_abc", "intent_type":"rag"}                        │
│         │                                                           │
│         ▼                                                           │
│  Loki / ELK / Console                                              │
│                                                                      │
├─────────────────────────────────────────────────────────────────────┤
│                                                                      │
│  2. 追踪数据流                                                      │
│  ─────────────────────────────────────                             │
│                                                                      │
│  @traced(span_name="rag_retrieval")                                │
│  async def retrieve(query):                                        │
│         │                                                           │
│         ▼                                                           │
│  tracer.start_span("rag_retrieval")                                 │
│         │                                                           │
│         ├── 创建 Span                                               │
│         ├── 设置属性                                               │
│         └── 返回 Span                                               │
│         │                                                           │
│         ▼                                                           │
│  Span 生命周期                                                      │
│         │                                                           │
│         ├── start_time 记录                                        │
│         ├── 添加事件 add_event()                                    │
│         ├── 设置属性 set_attribute()                                │
│         └── end() 结束                                             │
│         │                                                           │
│         ▼                                                           │
│  OTel SDK → OTLP → Collector → Tempo                               │
│                                                                      │
├─────────────────────────────────────────────────────────────────────┤
│                                                                      │
│  3. 指标数据流                                                      │
```

#### 4.2.1 logging.py - structlog 使用

```python
"""
logging.py 核心代码解析

Q1: 为什么用 structlog 而不是标准 logging？

A1:
标准 logging 的问题：
1. 输出格式固定，难以结构化
2. JSON 输出需要手写 Formatter
3. 上下文传递需要自己处理

structlog 的优势：
1. 声明式配置
2. 内置 JSON/彩色输出
3. 自动上下文绑定

Q2: Processor 是什么？

A2:
Processor 是处理日志事件的函数，链式调用：

@traced -> log.info("完成") -> [P1, P2, P3, P4] -> JSON

每个 Processor 接收 event_dict，返回处理后的 event_dict

示例：
def add_trace_context(logger, method_name, event_dict):
    event_dict["trace_id"] = get_trace_id()
    return event_dict

Q3: 如何实现异步安全的上下文传递？

A3:
structlog 使用 contextvars 传递上下文：

from structlog.contextvars import merge_contextvars

structlog.configure(
    processors=[
        merge_contextvars,  # ← 自动从 contextvars 获取
        add_trace_context,
        JSONRenderer(),
    ]
)

设置上下文：
structlog.contextvars.bind_contextvars(trace_id="tr_abc")
"""

# 处理器定义
def add_trace_context_processor(logger, method_name, event_dict):
    """添加 Trace 上下文"""
    trace_id = get_trace_id()
    if trace_id:
        event_dict["trace_id"] = trace_id
    return event_dict

# 日志配置
structlog.configure(
    processors=[
        structlog.contextvars.merge_contextvars,  # 上下文合并
        add_trace_context_processor,              # 添加 trace 上下文
        structlog.stdlib.add_log_level,          # 添加日志级别
        structlog.dev.ConsoleRenderer(),         # 开发环境彩色输出
        # 或 structlog.processors.JSONRenderer()  # 生产环境 JSON
    ]
)

# 使用
logger = structlog.get_logger()
logger.info("意图识别完成",
    intent_type="rag",
    confidence=0.92,
    duration_ms=45
)
# 输出：
# 2024-01-15 14:30:00 [INFO] intent_detected
#   trace_id: tr_abc123
#   intent_type: rag
#   confidence: 0.92
#   duration_ms: 45
```

#### 4.2.2 trace.py - OpenTelemetry 使用

```python
"""
trace.py 核心代码解析

Q1: 什么是 Span？

A1:
Span 是追踪的基本单元，代表一个操作：

Trace (tr_abc)
└── Span: HTTP /api/v1/chat
    ├── Span: intent_detection
    │   └── Span: llm_call
    └── Span: rag_agent
        ├── Span: milvus_query
        └── Span: rerank

每个 Span 记录：
- 开始/结束时间
- 耗时
- 属性（key-value）
- 事件（时间点）

Q2: 为什么用装饰器而不是手动管理？

A2:
装饰器优势：
1. 自动创建和结束 Span
2. 自动处理异常
3. 代码简洁

@traced(span_name="my_func")
async def my_func():
    pass

# 等价于：
async def my_func():
    span = tracer.start_span("my_func")
    try:
        return await original_my_func()
    finally:
        span.end()

Q3: SpanKind 是什么？

A3:
SpanKind 表示 Span 的角色：

- INTERNAL: 内部操作（默认）
- SERVER: 服务端接收请求
- CLIENT: 客户端发起请求
- PRODUCER: 消息生产者
- CONSUMER: 消息消费者

示例：
tracer.start_span("http_request", kind=SpanKind.SERVER)
tracer.start_span("db_query", kind=SpanKind.CLIENT)
"""

from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor

# 配置
provider = TracerProvider()
provider.add_span_processor(BatchSpanProcessor(ConsoleSpanExporter()))
trace.set_tracer_provider(provider)

# 获取 Tracer
tracer = trace.get_tracer(__name__)

# 方式1: 装饰器
@traced(span_name="rag_retrieval")
async def retrieve(query: str):
    # 自动创建和结束 Span
    return await do_retrieval(query)

# 方式2: 手动管理
span = tracer.start_span("my_operation")
try:
    result = await do_something()
    span.set_status(StatusCode.OK)
except Exception as e:
    span.set_status(StatusCode.ERROR, str(e))
    span.record_exception(e)
    raise
finally:
    span.end()

# 添加事件
span.add_event("operation_complete", {"result_count": 5})

# 设置属性
span.set_attribute("retrieval_type", "hybrid")
```

#### 4.2.3 metrics.py - prometheus_client 使用

```python
"""
metrics.py 核心代码解析

Q1: Counter、Gauge、Histogram 区别？

A1:
Counter: 只能递增，用于计数
Gauge: 可增可减，用于当前值
Histogram: 记录分布，用于延迟

Q2: Histogram 的 buckets 是什么？

A2:
buckets 定义统计区间：

request_duration_seconds_bucket{le="0.1"} = 1000   # 1000个请求 < 100ms
request_duration_seconds_bucket{le="0.5"} = 5000   # 5000个请求 < 500ms
request_duration_seconds_bucket{le="1.0"} = 8000  # 8000个请求 < 1s
request_duration_seconds_bucket{le="+Inf"} = 10000 # 总共10000个请求

可计算百分位：
- P50 = 第一个达到 50% 的 bucket
- P90 = 第一个达到 90% 的 bucket

Q3: 标签（Labels）的作用？

A3:
标签用于多维度分析：

# 无标签
requests_total = 10000

# 有标签
requests_total{endpoint="/chat"} = 5000
requests_total{endpoint="/search"} = 3000
requests_total{endpoint="/admin"} = 2000

好处：
1. 可过滤：只看 /chat 的请求
2. 可聚合：计算各端点占比
3. 可分析：对比不同端点性能
"""

from prometheus_client import Counter, Histogram, Gauge

# 定义指标
REQUEST_COUNT = Counter(
    "http_requests_total",
    "Total HTTP requests",
    ["method", "endpoint", "status"]
)

REQUEST_LATENCY = Histogram(
    "http_request_duration_seconds",
    "Request latency",
    ["method", "endpoint"],
    buckets=(0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1.0)
)

ACTIVE_CONNECTIONS = Gauge(
    "active_connections",
    "Number of active connections"
)

# 使用
REQUEST_COUNT.labels(method="POST", endpoint="/chat", status="200").inc()
REQUEST_LATENCY.labels(method="POST", endpoint="/chat").observe(0.125)
ACTIVE_CONNECTIONS.set(42)

# 暴露 /metrics 端点
from prometheus_client import start_http_server
start_http_server(8000)  # http://localhost:8000/metrics
```

## 7. 面试高频问题

### 7.1 概念类问题

#### Q1: 什么是可观测性？和监控有什么区别？

```
参考答案：

监控（Monitoring）：
- 回答"系统是否健康"
- 关注：CPU、内存、网络等系统指标
- 被动：预设指标，超阈值告警

可观测性（Observability）：
- 回答"为什么系统这样表现"
- 关注：请求链路、业务语义、用户行为
- 主动：任意问题都可以定位

区别：
┌──────────────────┬──────────────────┐
│     监控          │    可观测性       │
├──────────────────┼──────────────────┤
│ 问：系统健康吗？   │ 问：为什么这样？   │
│ 预设指标          │ 任意维度          │
│ 阈值告警          │ 根因分析          │
│ 被动              │ 主动              │
└──────────────────┴──────────────────┘

可观测性三大支柱：
1. 日志（Logs）：记录"发生了什么"
2. 追踪（Traces）：串联"怎么发生的"
3. 指标（Metrics）：统计"发生了多少"
```

#### Q2: 解释 trace_id、run_id、span 的区别？

```
参考答案：

trace_id（追踪 ID）：
- 一次完整请求的标识
- 从入口生成，沿整个链路传递
- 用于关联所有相关日志和追踪

run_id（运行 ID）：
- 标识一次 Agent 执行
- 与 trace_id 一对一（单轮）或一对多（多轮）
- 用于关联同一 Agent 的多次调用

span（跨度）：
- Trace 中的操作单元
- 有开始时间、结束时间、属性
- 形成树形结构（父子关系）

关系图：
trace_id: tr_abc123 (一次请求)
│
├── span: HTTP 入口 (root)
│   │
│   ├── span: 意图识别
│   │   └── span: LLM 调用
│   │
│   └── run_id: run_xyz789 (Agent 执行)
│       │
│       ├── span: RAG 检索
│       │   ├── span: Milvus 查询
│       │   └── span: Rerank
│       │
│       └── span: 生成答案
│           └── span: LLM 调用
```

#### Q3: OpenTelemetry 是什么？有哪些核心组件？

```
参考答案：

OpenTelemetry（OTel）：
- CNCF 毕业项目
- 分布式追踪的事实标准
- 供应商无关

核心组件：

1. API 层
   - TracerProvider：管理 Tracer
   - Tracer：创建 Span
   - Span：追踪单元

2. SDK 层
   - SpanProcessor：处理 Span
   - Sampler：采样策略
   - Resource：资源信息

3. Exporter 层
   - OTLP Exporter：标准协议
   - Jaeger Exporter：Jaeger 后端
   - Zipkin Exporter：Zipkin 后端

4. Collector（可选）
   - 接收、处理、导出数据
   - 支持采样、过滤、路由
```

#### Q4: 如何设计高可观测性的 Agent 系统？

```
四大支柱：
```

#### Q5: 如何实现跨服务追踪？

```
参考答案：

方案：OpenTelemetry

1. trace_id 生成
   - 请求入口生成
   - 使用 W3C Trace Context 标准

2. 上下文传递
   - HTTP Header：traceparent
   - 格式：00-{trace_id}-{span_id}-{flags}

3. 自动埋点
   - OTel SDK 自动注入 Header
   - 无需手动传递

4. 采样策略
   - 头部采样：固定比例
   - 尾部采样：慢请求/错误

实现示例：
# 服务 A
tracer = trace.get_tracer(__name__)
with tracer.start_as_current_span("operation") as span:
    # 自动注入 trace_id 到 Header
    response = requests.post(url, headers={})

# 服务 B
# 自动从 Header 获取 trace_id
span = tracer.start_span("downstream")
```

### 7.3 实践类问题

#### Q6: Python 中如何实现异步上下文传递？

```
参考答案：

使用 contextvars（Python 3.7+）：

from contextvars import ContextVar

trace_id: ContextVar[str] = ContextVar("trace_id", default=None)

# 设置
trace_id.set("tr_abc123")

# 获取
print(trace_id.get())  # "tr_abc123"

# 异步传递
async def child():
    # 自动继承 trace_id
    print(trace_id.get())  # "tr_abc123"

async def parent():
    trace_id.set("tr_abc123")
    await child()

为什么不用 threading.local？
- 协程切换时可能丢失上下文
- 同一线程执行多个协程会冲突

contextvars 的优势：
- 每个协程独立上下文
- await 自动传递上下文
- 线程安全 + 协程安全
```

#### Q7: 如何评估 RAG 系统性能？需要哪些指标？

```
参考答案：

核心指标：

1. 检索质量
   - Hit Rate：正确答案在结果中的比例
   - MRR（Mean Reciprocal Rank）：排名倒数均值
   - NDCG：考虑排名的评估

2. 性能指标
   - 检索延迟：P50、P90、P99
   - Token 消耗：prompt_tokens + completion_tokens
   - 端到端延迟

3. 业务指标
   - 用户满意度
   - 澄清率
   - 答案引用准确率

Prometheus 指标定义：
rag_retrieval_total{type="hybrid"} - 检索次数
rag_retrieval_duration_seconds{type="hybrid"} - 检索延迟
rag_retrieval_hits_total{type="exact|partial|miss"} - 命中率
llm_tokens_total - Token 消耗
```
