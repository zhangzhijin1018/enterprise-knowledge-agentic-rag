# 第一章：业务功能详解

## 1.1 合同审查是什么？

### 问：什么是合同审查？为什么要做合同审查？

**答**：合同审查是法务人员对合同文本进行系统性检查，识别潜在风险点，生成审查报告的过程。

**传统方式 vs 智能方式**：

```
┌─────────────────────────────────────────────────────────────┐
│                     传统方式（人工审查）                        │
├─────────────────────────────────────────────────────────────┤
│  1. 法务人员逐条阅读合同                                    │
│  2. 对照法规和模板判断条款是否合规                          │
│  3. 手工记录风险点                                          │
│  4. 撰写审查报告                                            │
│  问题：效率低、标准不统一、容易遗漏                          │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│                     智能方式（AI审查）                        │
├─────────────────────────────────────────────────────────────┤
│  1. 上传合同文件                                            │
│  2. AI 自动解析合同结构                                     │
│  3. 检索相关法规和标准模板                                   │
│  4. AI 自动识别风险点                                       │
│  5. 生成结构化审查报告                                      │
│  6. 高风险项自动触发人工复核                                │
│  优势：效率高、标准统一、可审计、全程记录                    │
└─────────────────────────────────────────────────────────────┘
```

---

## 1.2 合同审查能做什么？

### 问：这个系统能审查哪些类型的合同？

**答**：系统支持多种合同类型，通过智能识别自动匹配：

| 合同类型 | 特点 | 风险关注点 |
|----------|------|-----------|
| 采购合同 | 设备采购、物资采购 | 付款条件、验收标准、违约责任 |
| 服务合同 | 运维、技术服务 | 服务范围、保密条款、变更权 |
| 建设合同 | 工程施工、建设安装 | 工期要求、安全责任、无限连带 |
| 劳动合同 | 人员聘用 | 竞业限制、保密义务、解除条件 |
| 销售合同 | 产品销售 | 质量保证、交货条件、风险转移 |

# 第三章：设计理念详解

## 3.1 为什么用 LangGraph？

### 问：为什么选择 LangGraph 而不是直接写 Python 代码？

**答**：LangGraph 提供了状态机能力，让复杂工作流可维护、可追踪：

| 对比 | 直接写代码 | LangGraph |
|------|-----------|-----------|
| 状态管理 | 手动维护 dict | 自动状态流转 |
| 流程控制 | if/else 判断 | 条件边定义 |
| 可视化 | 无 | 支持图形化 |
| 断点恢复 | 难实现 | 内置支持 |
| 并行执行 | 复杂 | 简单配置 |

**LangGraph 核心概念**：

```
┌─────────────────────────────────────────────────────────────┐
│                      LangGraph 核心概念                       │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  StateGraph                                                 │
│    ├── state: 共享状态（dict）                               │
│    ├── node: 节点（函数）                                    │
│    ├── edge: 边（节点间的连接）                              │
│    └── conditional_edge: 条件边（根据状态决定下一步）         │
│                                                             │
│  工作流程                                                    │
│    graph = StateGraph(ContractState)                        │
│    graph.add_node("entry", entry_function)                 │
│    graph.add_node("react_loop", react_loop_function)       │
│    graph.add_edge("entry", "react_loop")                   │
│    graph.add_edge("react_loop", END)                       │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 3.2 为什么要用 ReAct 模式？

### 问：ReAct 模式是什么？为什么用它？

**答**：ReAct = Reasoning + Acting，让 AI 思考后再行动：

```
┌─────────────────────────────────────────────────────────────┐
│                        ReAct 循环                           │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│      ┌──────────┐                                           │
│      │  Think   │  ← AI 分析当前状态，决定下一步做什么       │
│      └────┬─────┘                                           │
│           │                                                 │
│           ▼                                                 │
│      ┌──────────┐                                           │
│      │  Plan    │  ← AI 制定计划，选择使用哪个工具           │
│      └────┬─────┘                                           │
│           │                                                 │
│           ▼                                                 │
│      ┌──────────┐                                           │
│      │   Act    │  ← AI 调用工具执行操作                    │
│      └────┬─────┘                                           │
│           │                                                 │
│           ▼                                                 │
│      ┌──────────┐                                           │
│      │ Observe  │  ← AI 获取工具返回结果                    │
│      └────┬─────┘                                           │
│           │                                                 │
│           │  ┌──────────────┐                               │
│           └─→│  反思：结果   │                               │
│              │  是否满意？   │                               │
│              └───────┬──────┘                               │
│                      │                                      │
│              ┌───────┴───────┐                              │
│              ▼               ▼                              │
│         ┌─────────┐     ┌─────────┐                        │
│         │   Yes   │     │   No    │                        │
│         │  结束   │     │ 继续循环 │                        │
│         └─────────┘     └─────────┘                        │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**ReAct 的优势**：
1. **可解释**：每个步骤都有思考过程
2. **可控**：可以限制调用次数
3. **可审计**：记录所有 tool call
4. **灵活**：可以动态选择工具

## 3.3 为什么需要 Human Review？

### 问：AI 都分析了，为什么还要人工复核？

**答**：这是国企合规的硬性要求：

| 场景 | AI判断 | 人工复核 |
|------|--------|----------|
| 低风险合同 | ✅ 直接通过 | ❌ 不需要 |
| 中风险合同 | ⚠️ 给建议 | 📋 可选复核 |
| **高风险合同** | 🔴 LLM判断 | **🔴 必须复核** |

**高风险定义**：
- 无限连带责任条款
- 单方面无条件解除权
- 违约金超过合同金额 30%
- 安全责任无限连带

## 4.4 Step 3：Contract Agent Server

### 问：Contract Agent Server 做什么？

**答**：基于 A2A 协议处理合同审查任务，编排 LangGraph 工作流：

```python
# apps/agents/contract_agent_server.py

class ContractAgentServer(A2AServer):
    """Contract Agent A2A 服务器 - 基于 LangGraph ReAct 模式。"""

    async def handle_task(self, task):
        """处理 A2A 任务。"""
        # 1. 提取消息内容
        query = task.message.get("content", {}).get("text", "")

        # 2. 提取元数据
        metadata = task.metadata or {}
        contract_file_id = metadata.get("contract_file_id")
        contract_name = metadata.get("contract_name")
        contract_type = metadata.get("contract_type")

        # 3. 执行合同审查工作流
        result = await self._execute_review_workflow(
            run_id=task.id,
            trace_id=metadata.get("trace_id"),
            query=query,
            contract_file_id=contract_file_id,
            contract_name=contract_name,
            contract_type=contract_type,
            ...
        )

        # 4. 处理 Human Review 情况
        if result.get("outcome") == "review":
            self._create_human_review_task(result)

        # 5. 返回结果
        return task

    async def _execute_review_workflow(self, ...):
        """执行合同审查工作流（ReAct 模式）。"""
        # 创建初始状态
        initial_state = create_initial_contract_state(...)

        # 执行 LangGraph 工作流
        result = self._graph.invoke(initial_state)

        return result
```

**实际链路**：

```

    ↓ A2A 调用
Contract Agent Server (contract_agent_server.py)
    ↓ 调用
LangGraph 工作流 (core/agent/workflows/contract/graph.py)
    ↓
审查结果 + Human Review 任务
```

# core/agent/workflows/contract/graph.py

def create_contract_graph(nodes) -> StateGraph:
    graph = StateGraph(ContractWorkflowState)
    
    # 添加节点
    graph.add_node("entry", nodes.entry)
    graph.add_node("react_loop", nodes.react_loop)
    graph.add_node("reflect", nodes.reflect)
    graph.add_node("human_review", nodes.human_review)
    graph.add_node("generate_report", nodes.generate_report)
    graph.add_node("finish", nodes.finish)
    
    # 定义边
    graph.set_entry_point("entry")
    graph.add_edge("entry", "react_loop")
    graph.add_edge("react_loop", "reflect")
    graph.add_edge("reflect", "generate_report")
    graph.add_edge("reflect", "human_review")  # 高风险时走这里
    graph.add_edge("human_review", "generate_report")
    graph.add_edge("generate_report", "finish")
    graph.add_edge("finish", END)
    
    return graph.compile()
```

```python
@tool("extract_clauses", args_schema=ExtractClausesInput, return_direct=False)
def extract_clauses(
    contract_text: str,
    contract_type: Optional[str] = None,
    run_manager: Optional[CallbackManagerForToolRun] = None,
) -> dict:
    """抽取合同条款，识别关键要素，并提取法律检索主题供 search_laws 使用。

    全 LLM 提取设计：
    - 条款提取（clauses）：使用 LLM 理解合同内容，智能识别条款结构
    - 当事人信息（parties）：使用 LLM 提取
    - 缺失条款检测（missing_clauses）：使用 LLM 判断缺少哪些必要条款
    - 法律检索主题（legal_search_topics）：LLM 生成，用于 search_laws 多路检索
    - 法律问题（contract_legal_issues）：LLM 生成，用于风险分析

    与传统正则规则提取的区别：
    | 功能 | 正则规则 | LLM（全方案） |
    |------|----------|---------------|
    | 条款识别 | 只能匹配"第X条" | 理解语义，识别各种格式 |
    | 条款类型 | 关键词匹配 | 理解含义，准确分类 |
    | 风险识别 | 固定关键词 | 理解语义，智能识别 |
    | 缺失条款 | 简单判断 | 理解合同类型和上下文 |
    """
    logger.info(f"[Tool:extract_clauses] 开始抽取条款（全 LLM 版）")

    try:
        # 调用 LLM 提取所有信息
        llm_result = _extract_all_with_llm(
            contract_text=contract_text,
            contract_type=contract_type,
        )

        if llm_result is None:
            logger.error("[Tool:extract_clauses] LLM 提取失败")
            return {
                "status": "error",
                "message": "LLM 提取失败，请检查 LLM 服务是否可用",
                "clauses": [],
                "parties": [],
                "missing_clauses": [],
                "legal_search_topics": [],
                "contract_legal_issues": [],
            }

        return {
            "status": "success",
            "clauses": llm_result.get("clauses", []),
            "parties": llm_result.get("parties", []),
            "missing_clauses": llm_result.get("missing_clauses", []),
            "legal_search_topics": llm_result.get("legal_search_topics", []),
            "contract_legal_issues": llm_result.get("contract_legal_issues", []),
        }

    except Exception as e:
        logger.error(f"[Tool:extract_clauses] 抽取失败: {e}", exc_info=True)
        return {
            "status": "error",
            "message": str(e),
            "clauses": [],
            "parties": [],
            "missing_clauses": [],
            "legal_search_topics": [],
            "contract_legal_issues": [],
        }


def _extract_all_with_llm(
    contract_text: str,
    contract_type: Optional[str],
) -> Optional[dict]:
    """使用 LLM 从合同文本中提取所有信息。

    LLM 会分析合同内容，一次性提取：
    1. clauses: 合同条款列表（条款ID、类型、内容、风险指示）
    2. parties: 当事人信息
    3. missing_clauses: 疑似缺失的必要条款
    4. legal_search_topics: 法律检索主题
    5. contract_legal_issues: 法律问题
    """
    contract_type_hint = f"合同类型：{contract_type}" if contract_type else "合同类型：未指定"

    prompt = f"""你是一个专业的合同法律审查助手。请分析以下合同内容，提取完整的条款信息。

{contract_type_hint}

合同全文：
---
{contract_text}
---

请以 JSON 格式提取以下信息：

1. clauses: 合同条款列表
   - clause_id: 条款编号（如"第1条"）
   - clause_type: 条款类型（标的条款/价款条款/履行期限/质量标准/违约责任/争议解决/保密条款/其他条款）
   - clause_title: 条款标题（条款内容的前50字）
   - clause_content: 条款完整内容
   - risk_indicators: 风险指示器列表
     * 格式如："[高风险] 无条件解除" 或 "[中风险] 违约金偏高"

2. parties: 当事人信息列表
   - name: 当事人名称
   - role: 角色（甲方/乙方/丙方等）

3. missing_clauses: 疑似缺失的必要条款类型

4. legal_search_topics: 法律检索主题列表（3-8个）
   - 用于检索相关法规的关键词/短语
   - 应基于合同中的风险点和法律问题生成

5. contract_legal_issues: 合同涉及的法律问题列表（2-5个）
"""
    response = llm.chat(messages=[LLMMessage(role="user", content=prompt)], model=None)
    content = response.content.strip()
    if "```json" in content:
        content = content.split("```json")[1].split("```")[0]
    elif "```" in content:
        content = content.split("```")[1].split("```")[0]
    return json.loads(content)
```

### 工具4.1：search_laws（检索法规 - 支持相关性阈值过滤）

```python
@tool
def search_laws(tool_input: dict) -> dict:
    """检索相关法律法规，支持多路检索和相关性阈值过滤。

    优化说明：
    - 支持接收 LLM 提取的 legal_search_topics
    - 支持接收合同全文 content
    - 使用多路检索策略，从多个法律角度并行检索
    - 使用相关性阈值（min_relevance）替代固定数量过滤

    返回策略：
    - 返回相关性 >= min_relevance 的结果
    - 最多返回 max_results 条
    - 避免因固定数量限制而漏掉相关结果

    输入：
        query: 检索query
        contract_type: 合同类型
        business_domain: 业务域
        top_k: 每路检索的召回数量（用于合并前的初筛）
        min_relevance: 最低相关性阈值（默认0.4）
        max_results: 最大返回数量（默认10）
        extracted_clauses: 已抽取的条款列表（可选）
        contract_content: 合同全文（可选）
        legal_search_topics: LLM 提取的法律检索主题（可选，优先级最高）

    输出：
        status: 状态
        count: 检索数量
        laws: 法规列表（已按相关性排序）
        retrieval_method: 检索方法（multi/basic/fallback）
    """
    query = tool_input.get("query", "")
    contract_type = tool_input.get("contract_type")
    business_domain = tool_input.get("business_domain", "能源")
    top_k = tool_input.get("top_k", 5)
    min_relevance = tool_input.get("min_relevance", 0.4)
    max_results = tool_input.get("max_results", 10)
    legal_search_topics = tool_input.get("legal_search_topics")

    # 如果有 legal_search_topics，使用多路检索
    if legal_search_topics:
        laws = rag_service.search_laws_multi(
            query=query,
            contract_type=contract_type,
            business_domain=business_domain,
            top_k=top_k,
            min_relevance=min_relevance,
            max_results=max_results,
            legal_search_topics=legal_search_topics,
        )
        retrieval_method = "multi"
    else:
        laws = rag_service.search_laws(
            query=query,
            contract_type=contract_type,
            business_domain=business_domain,
            top_k=max_results,
        )
        retrieval_method = "basic"

    return {
        "status": "success",
        "count": len(laws),
        "laws": [law.model_dump() for law in laws],
        "retrieval_method": retrieval_method,
    }
```

**相关性分数（relevance）计算原理**：

```
┌─────────────────────────────────────────────────────────────┐
│                  RAG 检索链路 - 相关性分数计算                  │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  阶段1: Hybrid Search（混合检索）                           │
│  ├── Dense Retrieval: BGE-M3 语义向量相似度                │
│  └── Sparse Retrieval: BM25 关键词匹配                     │
│  └── fusion_score = α × dense + (1-α) × sparse            │
│  └── 输出: 召回 top_k (20条) 候选文档                     │
│                                                             │
│  阶段2: Rerank（重排序）                                   │
│  ├── 使用 BGE-Reranker (Cross-Encoder)                    │
│  ├── 输入: (query, document) → 语义相关性分数             │
│  ├── 分数归一化: rerank_score / max_score                 │
│  └── 输出: 精排序 top_n (5条) + rerank_score             │
│                                                             │
│  多路检索合并时：                                           │
│  ├── 基础分: max(各路 rerank_score)                        │
│  ├── 命中奖励: count × 0.02 (最多 +0.1)                   │
│  └── 最终分: min(基础分 + 奖励, 1.0)                      │
│                                                             │
│  返回策略：                                                 │
│  ├── 过滤: relevance >= min_relevance (默认 0.4)          │
│  └── 截断: 最多返回 max_results 条 (默认 10)              │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

推荐保持当前的 `score / max_score`，原因：

1. 简单高效
2. 保留相对排序
3. 与 min_relevance=0.4 配合良好
4. 后续有命中奖励做二次调整

┌─────────────────────────────────────────────────────────────────┐
│                    推荐：不建议用 softmax                               │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  原因：                                                         │
│                                                                 │
│  1. Cross-Encoder 的分数本身已经是"相对排序"                       │
│     → 不需要 softmax 再做一次"概率化"                             │
│                                                                 │
│  2. softmax 会放大差距，可能导致：                                │
│     → 高分 doc: 0.90 → softmax后: 0.68                        │
│     → 中分 doc: 0.60 → softmax后: 0.22  ← 被大幅压缩            │
│     → 低分 doc: 0.45 → softmax后: 0.09 ← 几乎消失             │
│                                                                 │
│  3. 后续有 min_relevance=0.4 过滤                               │
│     → softmax 可能导致很多"合理"的中间文档被过滤掉                 │
│                                                                 │
│  4. 后续还有多路合并 + 命中奖励                                   │
│     → 多层调整让 softmax 的"概率"意义变得模糊                     │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘

**为什么使用相关性阈值而不是固定数量**：

| 问题 | 固定 top_k 的问题 | 相关性阈值的优势 |
|------|-------------------|-----------------|
| 法律检索 | 语义相近的法规多 | 只返回真正相关的 |
| 数量不确定 | 可能返回 0 条 | 至少返回 1 条（如果有相关） |
| 阈值调优 | 无 | min_relevance=0.4 适合法律场景 |

**为什么选择 0.4 作为默认值？**

```
┌─────────────────────────────────────────────────────────────────┐
│                    0.4 是经验值，非精确计算                             │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  原因：我们没有标注数据！                                         │
│                                                                 │
│  ├── 法律检索没有人工标注的 (query, relevant_laws) 对              │
│  ├── 无法绘制 PR 曲线                                            │
│  ├── 无法计算真实 F1                                             │
│  └── 只能靠经验设定                                              │
│                                                                 │
│  0.4 的来源：                                                    │
│  ├── Cross-Encoder 输出范围通常是 [0, 1]                        │
│  ├── 0.5 通常是"明显相关"的边界                                 │
│  ├── 0.3 通常是"可能相关"的边界                                 │
│  └── 0.4 ≈ 0.5 和 0.3 的中间值                                 │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

**使用 context_precision 和 context_recall 进行评估**

由于 `search_laws` 只返回检索结果，不需要生成答案，所以只需评估检索质量：

```python
from ragas import evaluate
from ragas.metrics import context_precision, context_recall
from ragas import Dataset

# 1. 构建 RAGAS 数据集格式
# search_laws 只需要：user_input + reference + contexts（不需要 answer）

eval_dataset = Dataset.from_list([
    {
        "user_input": item["user_input"],
        "reference": item["reference"],
        # contexts 将在评估时通过 search_laws 获取
    }
    for item in search_laws_test_dataset
])

# 2. 定义评估函数（用于单样本评估）
def evaluate_single_retrieval(test_case: dict, threshold: float = 0.4) -> dict:
    """评估单次检索的 context_precision 和 context_recall。

    Args:
        test_case: 测试用例，包含 user_input 和 reference
        threshold: min_relevance 阈值

    Returns:
        包含 contexts 和评估指标的字典
    """
    from core.agent.workflows.contract.tools import search_laws

    # 调用 search_laws 获取检索结果
    result = search_laws(
        query=test_case["user_input"],
        min_relevance=threshold,
        max_results=10,
    )

    # 提取 contexts（法律条款内容）
    contexts = [law.get("article", "") for law in result.get("laws", [])]

    return {
        "user_input": test_case["user_input"],
        "reference": test_case["reference"],
        "contexts": contexts,
    }

# 3. 运行评估
results = []
for test_case in search_laws_test_dataset:
    eval_result = evaluate_single_retrieval(test_case, threshold=0.4)
    results.append(eval_result)

# 4. 构建评估数据集
eval_dataset = Dataset.from_list(results)

# 5. 运行 RAGAS 评估（只评估检索质量）
evaluation = evaluate(
    dataset=eval_dataset,
    metrics=[
        context_precision,  # 上下文精确率：检索到的上下文是否与参考答案相关
        context_recall,     # 上下文召回率：参考答案中的信息有多少被检索到
    ],
)

# 6. 输出结果
print("=" * 60)
print("search_laws 检索质量评估结果")
print("=" * 60)
print(f"min_relevance = 0.4")
print(f"测试用例数量 = {len(search_laws_test_dataset)}")
print()
print(f"context_precision (上下文精确率) = {evaluation['context_precision']:.4f}")
print(f"context_recall (上下文召回率)     = {evaluation['context_recall']:.4f}")
print()

# 7. 综合分数
composite_score = (evaluation['context_precision'] + evaluation['context_recall']) / 2
print(f"综合分数 (平均) = {composite_score:.4f}")
print("=" * 60)

**阈值科学优化方法（RAGAS 评估）**

min_relevance = 0.4 是经验值，
如果要科学优化，需要：
1. 收集测试集（问题 + 参考答案）
2. 用不同阈值运行 RAG 链路
3. 用 RAGAS 评估生成质量
4. 选择 RAGAS 分数最高的阈值

RAG 任务是生成式任务，不能用传统分类的 P/R/F1，需要用 RAGAS 框架评估。

**RAGAS 各指标计算原理公式**

RAGAS（Retrieval-Augmented Generation Assessment）是一套用于评估 RAG 系统质量的框架，各指标的计算原理如下：

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                          RAGAS 指标计算原理                                  │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  1. Faithfulness（忠诚度）                                                  │
│  ─────────────────────────────────────────────────────────────────────────  │
│  衡量：生成答案是否忠实于检索到的上下文，是否存在幻觉（hallucination）。      │
│                                                                             │
│  计算步骤：                                                                 │
│  ① LLM 从答案中提取所有事实陈述（statements）                               │
│  ② 对每个事实陈述，LLM 判断是否可由上下文推断得出                            │
│  ③ Faithfulness = 有依据的事实陈述数 / 答案中总事实陈述数                     │
│                                                                             │
│  公式：                                                                     │
│  Faithfulness = |{s ∈ statements | s 可由 contexts 推断}| / |statements|   │
│                                                                             │
│  范围：[0, 1]，越高越好                                                    │
│  含义：答案中 80% 的陈述都能在上下文中找到依据，说明幻觉较少                  │
│                                                                             │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  2. Answer Relevancy（答案相关性）                                          │
│  ─────────────────────────────────────────────────────────────────────────  │
│  衡量：生成答案与用户问题的相关程度，答案是否真正回答了问题。                  │
│                                                                             │
│  计算步骤：                                                                 │
│  ① LLM 根据问题生成 N 个反向问题（counter-questions）                        │
│  ② 计算答案与每个反向问题的语义相似度（通常用余弦相似度）                    │
│  ③ Answer Relevancy = 平均相似度                                            │
│                                                                             │
│  公式：                                                                     │
│  Answer Relevancy = (1/N) × Σᵢ cos_similarity(answer, reverse_qᵢ)          │
│                                                                             │
│  范围：[0, 1]，越高越好                                                    │
│  含义：答案与问题的语义匹配度高，说明回答切题                                 │
│  注意：答案冗长不扣分，只有答非所问才扣分                                     │
│                                                                             │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  3. Context Relevancy（上下文相关性）                                       │
│  ─────────────────────────────────────────────────────────────────────────  │
│  衡量：检索到的上下文与问题的相关程度，用于评估检索质量。                     │
│                                                                             │
│  计算步骤：                                                                 │
│  ① LLM 从上下文中识别出回答问题必需的关键句子（sentences that matter）       │
│  ② 计算关键句子占整个上下文的比例                                            │
│  ③ Context Relevancy = 关键句子数 / 上下文总句子数                           │
│                                                                             │
│  公式：                                                                     │
│  Context Relevancy = |{s ∈ context | s 与 question 相关}| / |context|       │
│                                                                             │
│  范围：[0, 1]，越高越好                                                    │
│  含义：检索到的上下文中，90% 都与问题相关，说明检索精准                       │
│  注意：这个指标惩罚信息冗余，即使所有信息都相关但太多也会扣分                  │
│                                                                             │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  4. Context Precision（上下文精确率）                                       │
│  ─────────────────────────────────────────────────────────────────────────  │
│  衡量：在检索到的上下文中，高相关信息是否排在前面（位置权重）。                │
│                                                                             │
│  计算步骤：                                                                 │
│  ① 对每个上下文片段，计算其与参考答案（reference）的相关性分数               │
│  ② 使用加权平均计算，考虑片段位置（越靠前权重越高）                          │
│  ③ Context Precision = Σᵢ (precision_at_i × relevance_i) / Σᵢ relevance_i │
│                                                                             │
│  公式：                                                                     │
│  CP@k = (Σᵢ₌₁ᵏ ( relevance_i × Σⱼ₌₁ⁱ relevance_j )) / (k × Σᵢ₌₁ᵏ relevance_i)│
│                                                                             │
│  其中：                                                                     │
│  - k = 检索的上下文数量                                                     │
│  - relevance_i = 第 i 个上下文与参考答案的相关性分数（0 或 1，或连续值）    │
│  - precision_at_i = 前 i 个上下文中有多少是相关的                            │
│                                                                             │
│  范围：[0, 1]，越高越好                                                    │
│  含义：相关上下文排在越前面，分数越高                                        │
│  特殊情况：如果没有参考答案，则使用 ground truth 答案替代                    │
│                                                                             │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  5. Context Recall（上下文召回率）                                          │
│  ─────────────────────────────────────────────────────────────────────────  │
│  衡量：参考答案中有多少信息被检索到的上下文覆盖。                             │
│                                                                             │
│  计算步骤：                                                                 │
│  ① LLM 将参考答案分解为多个原子信息单元（atomic facts）                     │
│  ② 对每个原子信息，判断是否能从检索到的上下文中推断出来                        │
│  ③ Context Recall = 能推断出的信息数 / 参考答案总信息数                      │
│                                                                             │
│  公式：                                                                     │
│  Context Recall = |{f ∈ reference_facts | f 可由 contexts 推断}|           │
│                   / |reference_facts|                                        │
│                                                                             │
│  范围：[0, 1]，越高越好                                                    │
│  含义：参考答案中的关键信息都被检索到了，说明没有遗漏重要内容                  │
│  注意：这个指标只衡量检索质量，不衡量生成质量                                  │
│                                                                             │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  6. Context Entity Recall（上下文实体召回率）【进阶指标】                     │
│  ─────────────────────────────────────────────────────────────────────────  │
│  衡量：参考答案中的关键实体有多少被检索到的上下文覆盖。                       │
│                                                                             │
│  公式：                                                                     │
│  Context Entity Recall = |{e ∈ reference_entities | e 在 contexts 中}|      │
│                          / |reference_entities|                             │
│                                                                             │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  7. Noise Sensitivity（噪声敏感性）【进阶指标】                              │
│  ─────────────────────────────────────────────────────────────────────────  │
│  衡量：系统是否会被不相关的上下文干扰。                                      │
│                                                                             │
│  公式：                                                                     │
│  Noise Sensitivity = 被不相关上下文误导的陈述数 / 总陈述数                   │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

**RAGAS 指标与 RAG 链路阶段的对应关系**

```
┌──────────────────────────────────────────────────────────────────────────────┐
│                              RAG 链路阶段                                     │
│                                                                              │
│   Query ──────► Retrieval ──────► Generation ──────► Answer                │
│                 (检索阶段)         (生成阶段)         (答案输出)              │
│                                                                              │
│  ┌─────────────┬─────────────────────────────────────────┐                   │
│  │  检索质量   │  context_relevancy    上下文相关性       │                   │
│  │  (Retrieval│  context_precision     上下文精确率       │                   │
│  │   Quality) │  context_recall        上下文召回率       │                   │
│  ├─────────────┼─────────────────────────────────────────┤                   │
│  │  生成质量   │  faithfulness         忠诚度             │                   │
│  │  (Generation│  answer_relevancy     答案相关性         │                   │
│  │   Quality) │                                            │                   │
│  └─────────────┴─────────────────────────────────────────┘                   │
│                                                                              │
│  检索质量指标：衡量"找得好不好"                                              │
│  生成质量指标：衡量"答得好不好"                                              │
└──────────────────────────────────────────────────────────────────────────────┘
```

**RAGAS 评估维度说明**

| 指标 | 说明 | 权重建议 | 衡量什么 |
|------|------|---------|---------|
| faithfulness | 忠诚度 | 25% | 生成质量（答案是否忠实于上下文，无幻觉） |
| answer_relevancy | 答案相关性 | 30% | 生成质量（答案是否回答了问题） |
| context_relevancy | 上下文相关性 | 20% | 检索质量（检索到的上下文是否与问题相关） |
| context_precision | 上下文精确率 | 15% | 检索质量（上下文信息是否有用于回答问题） |
| context_recall | 上下文召回率 | 10% | 检索质量（真实答案中的信息有多少被检索到） |

**综合分数计算方法**

```python
# 方法1：等权重平均
composite = mean([faithfulness, answer_relevancy, context_relevancy,
                  context_precision, context_recall])

# 方法2：自定义权重（根据业务需求）
composite = (
    faithfulness * 0.25 +          # 幻觉风险高，需重点关注
    answer_relevancy * 0.30 +     # 回答质量最重要
    context_relevancy * 0.20 +     # 检索相关
    context_precision * 0.15 +      # 信息密度
    context_recall * 0.10          # 完整性
)

# 方法3：关注检索质量（法律场景）
composite = (context_relevancy + context_precision + context_recall) / 3

# 方法4：关注生成质量
composite = (faithfulness + answer_relevancy) / 2
```

## 4.8 Step 7：ReAct 循环详解

### 问：react_loop 节点是怎么工作的？

**答**：循环调用工具直到完成：

```python
# core/agent/workflows/contract/nodes.py

class ContractWorkflowNodes:
    def react_loop(self, state: ContractWorkflowState) -> dict:
        """ReAct 循环节点。"""

        # 1. 检查是否达到最大迭代
        if state["react_iterations"] >= state["max_iterations"]:
            return {"outcome": "finish"}

        # 2. 决定下一步工具
        next_tool = self._decide_next_tool(
            completed_tools=state["completed_tools"],
            state=state,
        )

        # 3. 如果没有更多工具，结束循环
        if next_tool is None:
            return {"outcome": "finish"}

        # 4. 执行工具
        tool_result = self._execute_tool(next_tool, state)

        # 5. 更新状态
        return {
            "completed_tools": state["completed_tools"] + [next_tool],
            "react_iterations": state["react_iterations"] + 1,
            **tool_result,  # 合并工具结果
        }

    def _decide_next_tool(
        self,
        completed_tools: list[str],
        state: dict,
    ) -> str | None:
        """决定下一步使用哪个工具。

        优化后的工具执行顺序：
        1. parse_contract - 解析合同（最先执行）
        2. extract_clauses - 抽取条款（在 search_laws 之前执行）
        3. search_laws - 检索法规（可使用 extract_clauses 的 LLM 提取结果）
        4. search_templates - 检索模板
        5. search_history - 检索历史案例（为风险分析提供参考）
        6. analyze_risk - 分析风险（结合法规、模板、历史案例）

        设计原因：
        - extract_clauses 会调用 LLM 从合同内容中提取法律检索主题（legal_search_topics），
          这些主题可以传递给 search_laws，实现更精准的多路法规检索
        - search_history 在 analyze_risk 之前执行，为风险分析提供历史案例参考
        """

        # 工具执行顺序（基于依赖关系优化）
        # extract_clauses 在 search_laws 之前，因为：
        # - extract_clauses 会提取 legal_search_topics 供 search_laws 使用
        # - 实现基于合同内容的精准多路检索
        # search_history 在 analyze_risk 之前，因为：
        # - 需要为风险分析提供历史案例的处理方式参考
        tool_sequence = [
            "parse_contract",      # 1. 解析合同（最先执行）
            "extract_clauses",    # 2. 抽取条款（在 search_laws 之前）
            "search_laws",         # 3. 检索法规（可使用 LLM 提取的检索主题）
            "search_templates",    # 4. 检索模板
            "search_history",     # 5. 检索历史案例（为风险分析提供参考）
            "analyze_risk",       # 6. 分析风险（结合法规、模板、历史案例）
        ]

        # 找出下一个未执行的工具
        for tool in tool_sequence:
            if tool not in completed_tools:
                return tool

        return None  # 所有工具都执行完了

### 简化反思器（降级方案）

当 LLM 反思不可用时，使用基于规则的 `SimpleReflection`：

```python
class SimpleReflection:
    """简化的反思器 - 基于规则的快速检查。
    
    当 LLM 不可用时，使用规则进行快速反思。
    """
    
    @staticmethod
    def reflect(
        clauses: list[dict],
        risks: list[dict],
        conclusion: str,
    ) -> ReflectionResult:
        """基于规则的快速反思。

        检查规则：
        1. 必须有条款数据
        2. 高风险必须有具体条款
        3. 结论必须与风险匹配
        """
        issues = []
        suggestions = []

        # 检查1：条款数据完整性
        if not clauses:
            issues.append({
                "type": "遗漏",
                "description": "未抽取到合同条款",
                "severity": "高",
            })
            suggestions.append("请重新解析合同文档")

        # 检查2：风险与条款匹配
        risk_clause_ids = {r.get("related_clause") for r in risks}
        clause_ids = {c.get("clause_id") for c in clauses}
        unmatched = risk_clause_ids - clause_ids

        if unmatched:
            issues.append({
                "type": "不匹配",
                "description": f"部分风险项找不到对应条款: {unmatched}",
                "severity": "中",
            })

        # 检查3：结论与风险匹配
        high_risk_count = len([r for r in risks if r.get("risk_type") == "high"])

        if high_risk_count > 0 and "高风险" not in conclusion:
            issues.append({
                "type": "误判",
                "description": "存在高风险项但结论未提及",
                "severity": "高",
            })
            suggestions.append("结论应明确提及高风险项")

        # 判断状态
        if not issues:
            status = "通过"
            confidence = "高"
        elif any(i.get("severity") == "高" for i in issues):
            status = "需改进"
            confidence = "低"
        else:
            status = "需改进"
            confidence = "中"

        # 判断是否需要人工复核
        needs_human_review = high_risk_count > 0

        return ReflectionResult(
            status=status,
            confidence=confidence,
            issues=issues,
            suggestions=suggestions,
            needs_additional_retrieval=len(issues) > 0,
            retrieval_queries=["补充检索相关法规"] if issues else [],
            needs_human_review=needs_human_review,
            raw_result="基于规则的快速反思",
        )
```

### 反思节点代码

```python
async def reflect(self, state: ContractWorkflowState) -> dict:
    """反思节点：对审查结果进行二次校验。

    核心职责：
    - 使用 LLM 反思审查质量
    - 检查是否有遗漏
    - 决定是否需要 Human Review
    """
    run_id = state["run_id"]

    logger.info(f"[{run_id}] 执行反思校验...")

    # 获取审查结果
    contract_name = state.get("contract_name", "未知合同")
    contract_type = state.get("contract_type")
    business_domain = state.get("business_domain", "能源")
    clauses = state.get("extracted_clauses", [])
    risks = state.get("identified_risks", [])
    conclusion = state.get("risk_summary", "")

    # 检查是否需要反思
    if not self._use_reflection or self.reflection_engine is None:
        # 不使用反思，直接进入报告
        return self._decide_next_after_reflect(state, None)

    try:
        # 执行反思
        reflection = await self.reflection_engine.reflect(
            contract_name=contract_name,
            contract_type=contract_type,
            business_domain=business_domain,
            clauses=clauses,
            risks=risks,
            conclusion=conclusion,
            laws_context=state.get("retrieved_laws", []),
            templates_context=state.get("retrieved_templates", []),
        )

        logger.info(
            f"[{run_id}] 反思完成 | status={reflection.status} | "
            f"confidence={reflection.confidence} | "
            f"issues={len(reflection.issues)}"
        )

        # 根据反思结果决定下一步
        return self._decide_next_after_reflect(state, reflection)

    except Exception as e:
        logger.error(f"[{run_id}] 反思执行失败: {e}", exc_info=True)
        # 使用简化反思
        simple_reflection = SimpleReflection.reflect(
            clauses=clauses,
            risks=risks,
            conclusion=conclusion,
        )
        return self._decide_next_after_reflect(state, simple_reflection)

def _decide_next_after_reflect(
    self,
    state: dict,
    reflection: Optional[ReflectionResult],
) -> dict:
    """根据反思结果决定下一步。"""
    # 检查是否需要人工复核
    if reflection and reflection.needs_human_review:
        logger.info("反思决定：需要人工复核")
        return {
            "current_stage": ContractWorkflowStage.HUMAN_REVIEW.value,
            "agent_status": AgentThought.WAITING_REVIEW.value,
            "outcome": ContractWorkflowOutcome.REVIEW.value,
            "reflection_result": reflection.to_dict() if reflection else None,
        }

    # 检查状态中的 need_human_review 标志
    if state.get("need_human_review"):
        return {
            "current_stage": ContractWorkflowStage.HUMAN_REVIEW.value,
            "agent_status": AgentThought.WAITING_REVIEW.value,
            "outcome": ContractWorkflowOutcome.REVIEW.value,
            "reflection_result": reflection.to_dict() if reflection else None,
        }

    # 直接生成报告
    return {
        "current_stage": ContractWorkflowStage.GENERATE_REPORT.value,
        "agent_status": AgentThought.FINISHED.value,
        "outcome": ContractWorkflowOutcome.CONTINUE.value,
        "reflection_result": reflection.to_dict() if reflection else None,
    }
```

| 反思阶段 | 说明 |
|---------|------|
| 触发时机 | ReAct 循环完成后，所有工具执行完毕 |
| 输入数据 | clauses、risks、conclusion、laws、templates |
| 反思维度 | 完整性、充分性、合理性、遗漏检测 |
| 输出结果 | status、confidence、issues、suggestions |
| 后续处理 | 通过 → 报告；需改进 → 复核或报告；错误 → 降级方案 |

class ContractWorkflowNodes:
    def human_review(self, state: ContractWorkflowState) -> dict:
        """Human Review 节点。"""
        
        # 1. 获取高风险项
        high_risks = [
            r for r in state["identified_risks"]
            if r.get("risk_type") == "high"
        ]
        
        if not high_risks:
            # 没有高风险，不需要复核
            return {"need_human_review": False}
        
        # 2. 创建复核任务
        review_task = human_review_service.create_review_task(
            run_id=state["run_id"],
            contract_name=state["contract_name"],
            risk_items=high_risks,
            review_reason=f"发现 {len(high_risks)} 个高风险项",
            contract_type=state["contract_type"],
        )
        
        # 3. 记录复核状态
        return {
            "need_human_review": True,
            "human_review_id": review_task.review_id,
            "human_review_status": "pending",
            "pending_risks": high_risks,
            "outcome": "review",  # 等待复核
        }

# 第七章：Checkpoint与持久化

## 7.1 什么是 Checkpoint？

### 问：为什么要 Checkpoint？

**答**：Checkpoint（检查点）是工作流执行过程中的"存档点"，用于：

| 场景 | 没有 Checkpoint | 有 Checkpoint |
|------|-----------------|---------------|
| 服务重启 | 工作流全部重来 | 从存档恢复 |
| 网络中断 | 数据全部丢失 | 从存档继续 |
| 长时间任务 | 无法追踪进度 | 随时保存进度 |
| 审计追溯 | 无状态记录 | 完整操作历史 |

**国企合规要求**：
- 长时间运行的任务必须支持断点恢复
- 所有状态变化必须有记录
- 服务中断不能导致工作丢失

## 7.3 快照管理器代码

### 问：代码怎么实现快照管理？

```python
# core/agent/workflows/contract/snapshot_manager.py

class WorkflowSnapshotManager:
    """工作流快照管理器。"""
    
    def create_snapshot(
        self,
        run_id: str,
        trace_id: str,
        state: Dict[str, Any],
        reason: str = "periodic",
        is_final: bool = False,
    ) -> WorkflowSnapshot:
        """创建状态快照。"""
        snapshot_id = f"snap_{uuid.uuid4().hex[:12]}"
        
        snapshot = WorkflowSnapshot(
            snapshot_id=snapshot_id,
            run_id=run_id,
            trace_id=trace_id,
            created_at=datetime.now(),
            current_stage=state.get("current_stage", ""),
            completed_tools=state.get("completed_tools", []),
            react_iterations=state.get("react_iterations", 0),
            full_state=state,  # 完整状态
            checkpoint_reason=reason,
            is_final=is_final,
        )
        
        # 保存到缓存和数据库
        self._snapshots[snapshot_id] = snapshot
        self._save_to_db(snapshot)
        
        return snapshot
    
    def restore_state(self, snapshot_id: str) -> Optional[Dict[str, Any]]:
        """从快照恢复状态。"""
        snapshot = self.get_snapshot(snapshot_id)
        if not snapshot:
            return None
        return snapshot.full_state  # 返回完整状态
```

## 7.4 Checkpoint 执行器

### 问：带 Checkpoint 的工作流怎么运行？

**答**：

```python
# core/agent/workflows/contract/checkpoint_runner.py

class CheckpointWorkflowRunner:
    """带Checkpoint的工作流执行器。"""
    
    def __init__(self, graph, checkpoint_interval: int = 3):
        self.graph = graph
        self.checkpoint_interval = checkpoint_interval
        self.snapshot_manager = get_snapshot_manager()
        self.audit_logger = get_audit_logger()
    
    async def run(self, initial_state: Dict[str, Any]) -> Dict[str, Any]:
        """运行工作流（带Checkpoint）。"""
        run_id = initial_state["run_id"]
        
        # 1. 创建初始快照
        self.snapshot_manager.create_snapshot(
            run_id=run_id,
            trace_id=initial_state.get("trace_id"),
            state=initial_state,
            reason="workflow_start",
        )
        
        # 2. 运行工作流
        result = self.graph.invoke(initial_state)
        
        # 3. 创建最终快照
        self.snapshot_manager.create_snapshot(
            run_id=run_id,
            trace_id=initial_state.get("trace_id"),
            state=result,
            reason="workflow_end",
            is_final=True,
        )
        
        return result
    
    async def resume(self, run_id: str) -> Dict[str, Any]:
        """从快照恢复工作流。"""
        # 1. 获取最新快照
        snapshot = self.snapshot_manager.get_latest_snapshot(run_id)
        
        # 2. 恢复状态
        restored_state = snapshot.full_state
        
        # 3. 继续执行
        return await self.run(restored_state)
```

# 第八章：审计日志系统

## 8.1 为什么需要审计日志？

### 问：国企项目为什么必须审计日志？

**答**：国企合规的硬性要求：

| 要求 | 说明 |
|------|------|
| **操作追溯** | 所有关键操作必须有记录，能事后追溯 |
| **责任明确** | 操作必须关联到具体的人（用户ID、角色） |
| **时间精确** | 操作时间必须精确到毫秒 |
| **不可篡改** | 审计日志必须防篡改，有校验和 |
| **不可删除** | 审计日志只能追加，不能删除 |
| **持久化存储** | 必须存入数据库，不能只打印日志 |

```python
# core/agent/workflows/contract/audit_logger.py

class AuditLogger:
    """审计日志记录器。"""
    
    def __init__(self):
        self._buffer: List[AuditLog] = []
        self._buffer_size = 100  # 缓冲区大小
    
    def log(
        self,
        run_id: str,
        trace_id: str,
        event_type: AuditEventType,
        action: str,
        user_id: str,
        user_role: str,
        **kwargs,
    ) -> str:
        """记录审计日志。"""
        audit_id = f"audit_{uuid.uuid4().hex[:16]}"
        
        audit_log = AuditLog(
            audit_id=audit_id,
            run_id=run_id,
            trace_id=trace_id,
            event_type=event_type,
            timestamp=datetime.now(),
            user_id=user_id,
            user_role=user_role,
            action=action,
            result="success",
            checksum=self._generate_checksum(...),  # 防篡改
            **kwargs,
        )
        
        # 添加到缓冲区
        self._buffer.append(audit_log)
        
        # 缓冲区满时写入数据库
        if len(self._buffer) >= self._buffer_size:
            self._flush()
        
        return audit_id
    
    def log_workflow_start(self, run_id, trace_id, user_id, user_role, contract_name):
        """记录工作流启动。"""
        return self.log(
            run_id=run_id,
            trace_id=trace_id,
            event_type=AuditEventType.WORKFLOW_START,
            action=f"启动合同审查工作流: {contract_name}",
            user_id=user_id,
            user_role=user_role,
        )
    
    def log_tool_call(self, run_id, trace_id, tool_name, tool_input, user_id):
        """记录工具调用。"""
        return self.log(
            run_id=run_id,
            trace_id=trace_id,
            event_type=AuditEventType.TOOL_CALL,
            action=f"调用工具: {tool_name}",
            tool_name=tool_name,
            user_id=user_id,
            details={"tool_input": tool_input},
        )
    
    def log_review_decision(
        self,
        run_id,
        trace_id,
        review_id,
        decision,
        reviewer_id,
        reviewer_name,
        comments,
    ):
        """记录复核决策。"""
        return self.log(
            run_id=run_id,
            trace_id=trace_id,
            event_type=AuditEventType.REVIEW_APPROVED if decision == "approved" 
                       else AuditEventType.REVIEW_REJECTED,
            action=f"人工复核{decision}: {reviewer_name}",
            user_id="system",
            operator_id=reviewer_id,
            operator_name=reviewer_name,
            details={
                "review_id": review_id,
                "decision": decision,
                "comments": comments,
            },
        )

# core/agent/conversation_manager.py

class ConversationManager:
    """多轮对话管理器。"""
    
    def __init__(self):
        self._conversations: Dict[str, ConversationContext] = {}
    
    def create_conversation(
        self,
        conversation_id: str,
        user_id: str,
    ) -> ConversationContext:
        """创建新会话。"""
        conv = ConversationContext(
            conversation_id=conversation_id,
            user_id=user_id,
            status=ConversationStatus.ACTIVE,
        )
        self._conversations[conversation_id] = conv
        return conv
    
    def add_message(
        self,
        conversation_id: str,
        message_id: str,
        role: str,  # user/assistant
        content: str,
    ):
        """添加消息到会话。"""
        conv = self._conversations.get(conversation_id)
        if conv:
            conv.add_message(message_id, role, content)
    
    def get_history(
        self,
        conversation_id: str,
        limit: int = None,
    ) -> List[dict]:
        """获取对话历史。"""
        conv = self._conversations.get(conversation_id)
        if conv:
            return conv.get_history(limit=limit)
        return []

def build_context_prompt(history: List[dict], current_query: str) -> str:
    """构建带上下文的 prompt。"""
    context = []
    
    # 添加历史消息
    for msg in history[-5:]:  # 最近 5 轮
        role = msg["role"]
        content = msg["content"]
        context.append(f"{role}: {content}")
    
    # 添加当前问题
    context.append(f"user: {current_query}")
    
    return "\n".join(context)

## 10.2 四个核心 Tool 的分类

### 问：为什么要区分检索类和生成类 Tool？

**答**：不同类型的 Tool 评估指标不同：

| Tool 类型 | Tool 名称 | 核心能力 | 评估重点 |
|-----------|-----------|----------|----------|
| **检索类** | `search_laws` | 从向量数据库检索相关法规 | 检索的准确性 |
| **检索类** | `search_templates` | 从向量数据库检索标准模板 | 检索的召回率 |
| **生成类** | `extract_clauses` | 用 LLM 从合同中抽取条款 | 生成是否忠实 |
| **生成类** | `analyze_risk` | 用 LLM 分析风险并生成建议 | 生成是否相关 |

**为什么评估指标不同？**

- **检索类**：输出是从数据库查出来的，评估的是"查得准不准、查得全不全"
- **生成类**：输出是 LLM 生成的，评估的是"生成的内容是否正确、是否有用"

## 10.3 RAGAS 指标体系

### 问：RAGAS 是什么？有哪些指标？

**答**：RAGAS（Retrieval-Augmented Generation Assessment）是专门评估 RAG 系统的框架。

```
┌─────────────────────────────────────────────────────────────────────────┐
│                         RAGAS 评估指标体系                              │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  ┌─────────────────────────────┐    ┌─────────────────────────────┐      │
│  │       检索类指标           │    │       生成类指标            │      │
│  ├─────────────────────────────┤    ├─────────────────────────────┤      │
│  │                             │    │                             │      │
│  │  Context Precision          │    │  Faithfulness              │      │
│  │  上下文精确率               │    │  忠实率                    │      │
│  │  "检索结果有多少是相关的？" │    │  "生成内容是否忠实于上下文？"│      │
│  │                             │    │                             │      │
│  │  Context Recall            │    │  Answer Relevance          │      │
│  │  上下文召回率               │    │  答案相关性                 │      │
│  │  "相关的有多少被检索到？"   │    │  "答案和问题有多相关？"     │      │
│  │                             │    │                             │      │
│  └─────────────────────────────┘    └─────────────────────────────┘      │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### 指标详解

#### 1. Context Precision（上下文精确率）

**定义**：Top-K 检索结果中有多少是真正相关的

**计算公式**：
```
Context Precision = 相关文档数 / 检索文档总数
```

**示例**：
```
查询："采购合同违约金上限"

检索结果：
1. 《民法典》585条 ✓ (相关)
2. 《刑法》条款 ✗ (不相关)
3. 《民法典》585条解释 ✓ (相关)

Context Precision = 2/3 = 0.67
```

#### 2. Context Recall（上下文召回率）

**定义**：所有相关文档中有多少被检索到

**计算公式**：
```
Context Recall = 检索到的相关文档 / 所有相关文档
```

**示例**：
```
标准答案（法务专家标注）：
- 《民法典》585条
- 《合同法司法解释二》29条
- 集团采购管理办法15条

检索结果：
- 《民法典》585条 ✓
- 《合同法司法解释二》29条 ✓
- 其他不相关内容...

Context Recall = 2/3 = 0.67
```

#### 3. Faithfulness（忠实率）

**定义**：生成的答案中有多少内容可以从检索到的上下文中找到依据

**计算公式**：
```
Faithfulness = 有依据的陈述数 / 总陈述数
```

**示例**：
```
上下文（检索到的法规）：
"违约金过分高于造成损失的30%，法院可适当减少"

生成的答案：
"根据民法典规定，违约金超过实际损失30%的，法院可以适当减少" ✓ 有依据
"违约金最低不得低于合同金额的10%" ✗ 上下文未提及
"双方可以约定任意金额的违约金" ✓ 有依据（双方约定）

Faithfulness = 2/3 = 0.67
```

#### 4. Answer Relevance（答案相关性）

**定义**：生成的答案与原始问题的相关程度

**计算方式**：通过 LLM 生成多个问题变体，比较与原问题的语义相似度

**示例**：
```
问题："采购合同违约金上限是多少？"

生成的答案A：
"根据民法典585条，违约金过分高于造成损失的30%的，法院可以适当减少。"

生成的问题变体：
- "违约金有什么限制？"
- "违约金过高怎么办？"
- "违约金怎么算？"

答案A与问题变体的语义相似度 → 高（答案相关）

---

生成的答案B：
"本合同甲方为某能源公司，乙方为某设备供应商..."

生成的问题变体：
- "谁是合同甲方？"
- "这是什么类型的合同？"

答案B与原问题的语义相似度 → 低（答非所问）
```

            recall = self._compute_context_recall(item)
            results.append(RetrievalResult(
                context_precision=precision,
                context_recall=recall,
            ))
        return results
    
    def evaluate_generation_tool(self, dataset):
        """评估生成类 Tool（extract_clauses, analyze_risk）
        
        评估指标：Faithfulness, Answer Relevance
        """
        results = []
        for item in dataset:
            # 计算忠实率
            faithfulness = self._compute_faithfulness(item)
            # 计算答案相关性
            relevance = self._compute_answer_relevance(item)
            results.append(GenerationResult(
                faithfulness=faithfulness,
                answer_relevance=relevance,
            ))
        return results
```

## 10.7 面试要点

### 问：面试时关于评估系统应该怎么回答？

**答**：以下是面试中的关键点和回答思路：

#### Q1：为什么用 RAGAS 而不是自研评估？

**回答要点**：
```
1. RAGAS 是经过社区验证的评估框架
2. 指标定义科学，有学术支撑
3. 避免重复造轮子，减少维护成本
4. 社区持续更新，可复用最新研究成果
```

**加分回答**：
```
"我们评估过自研方案的痛点：指标定义不统一、评估结果不稳定。
 RAGAS 解决了这些问题，而且支持 LLM-as-Judge，
 可以评估语义层面的质量。"
```

#### Q2：Context Precision 和 Context Recall 的区别？

**回答要点**：
```
Context Precision：查得准不准
- 公式：相关文档数 / 检索总数
- 关心的是：Top-K 结果中有多少是真正相关的

Context Recall：查得全不全
- 公式：检索到的相关文档 / 所有相关文档
- 关心的是：所有相关的文档有没有都被找到

类比：考试
- Precision = 做对的题 / 做的所有题（准确率）
- Recall = 做对的题 / 应该做对的所有题（覆盖率）
```

#### Q3：Faithfulness 怎么计算？

**回答要点**：
```
Faithfulness 评估的是"生成的内容有没有依据"

计算方法：
1. 将答案拆分成多个陈述
2. 检查每个陈述是否可以在上下文中找到依据
3. Faithfulness = 有依据的陈述数 / 总陈述数

示例：
上下文："违约金超过损失30%的，法院可以适当减少"
答案："违约金超过损失30%的，法院可以适当减少，最高不超过..."
      ↓
陈述1："违约金超过损失30%的，法院可以适当减少" ✓ 有依据
陈述2："最高不超过..." ✗ 上下文未提及

Faithfulness = 1/2 = 0.5
```

#### Q4：数据集怎么保证质量？

**回答要点**：
```
1. 数据来源：历史审查记录 + 法务专家标注
2. 脱敏处理：移除公司名、金额、个人信息
3. 多人标注：交叉验证，提高一致性
4. 格式校验：JSON Schema 验证
5. 定期更新：补充新案例，删除失效案例
```

**加分回答**：
```
"我们的 ground_truth 是由法务部门专家标注的，
 每个案例都经过 2 名以上法务人员审核。
 标注完成后还会进行一致性检查，
 只有一致性 > 0.8 的案例才会纳入数据集。"
```

#### Q5：评估结果怎么用于改进？

**回答要点**：
```
1. 定位瓶颈：哪个 Tool 指标最低
2. 案例分析：哪些案例效果差，为什么
3. 针对性优化：
   - Precision 低 → 优化检索排序（Reranker）
   - Recall 低 → 优化检索召回（Query Rewrite）
   - Faithfulness 低 → 优化 Prompt 或使用更强模型
4. 回归测试：优化后重新评估，确保不退化
```

**加分回答**：
```
"我们建立了评估驱动的优化闭环：
 评估 → 发现问题 → 定位原因 → 优化代码 → 重新评估
 每次优化都要通过评估测试才能上线，
 这保证了系统的质量稳定性。"
```
