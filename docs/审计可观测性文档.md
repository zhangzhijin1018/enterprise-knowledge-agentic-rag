## 1. 概念入门：什么是可观测性？

### 1.1 从"监控"到"可观测性"

```
传统监控（Monitoring）：
┌─────────────────────────────────────────────────────────────────┐
│                                                                  │
│   监控仪表盘                                                       │
│   ┌─────────┐  ┌─────────┐  ┌─────────┐                       │
│   │ CPU 80% │  │ 内存 70%│  │ 磁盘 50%│                       │
│   └─────────┘  └─────────┘  └─────────┘                       │
│                                                                  │
│   只能看到：系统资源指标                                          │
│   无法回答：为什么 CPU 高？哪个用户的请求导致的？                   │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘

可观测性（Observability）：
┌─────────────────────────────────────────────────────────────────┐
│                                                                  │
│   可观测性平台                                                     │
│   ┌─────────────────────────────────────────────────────────┐   │
│   │  trace_id: tr_abc123                                    │   │
│   │  user_id: user_001                                     │   │
│   │  intent: analytics_query                                │   │
│   │  ├─ intent_detection: 45ms ✅                          │   │
│   │  ├─ rag_retrieval: 120ms ✅                            │   │
│   │  │   └─ milvus_query: 80ms ✅                          │   │
│   │  ├─ llm_call: 500ms ✅                                 │   │
│   │  └─ total: 665ms ✅                                    │   │
│   └─────────────────────────────────────────────────────────┘   │
│                                                                  │
│   能看到：完整调用链 + 业务语义 + 性能分析                         │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### 1.2 为什么 Agent 平台需要可观测性？

Agent 平台的特点决定了它需要更强的可观测性：

| 特点 | 带来的挑战 | 可观测性解决方案 |
|------|------------|----------------|
| **多 Agent 协作** | 调用链路复杂 | Trace 追踪 |
| **LLM 调用** | 成本高、延迟高 | Token 指标 |
| **RAG 检索** | 检索质量难评估 | 命中率指标 |
| **高风险操作** | 合规要求 | 审计日志 |
| **用户数据访问** | 安全要求 | 数据访问审计 |
| **对话多轮** | 状态管理复杂 | Session 追踪 |

### 1.3 核心概念：trace_id、run_id、span

```
┌─────────────────────────────────────────────────────────────────┐
│                    核心概念解析                                    │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  trace_id（追踪 ID）：                                            │
│  ─────────────────────────────────────                          │
│  • 一次完整请求的唯 一标识                                        │
│  • 从请求入口生成，沿整个调用链传递                                │
│  • 格式：tr_ + 16位十六进制（tr_a1b2c3d4e5f60718）               │
│                                                                  │
│  run_id（运行 ID）：                                             │
│  ─────────────────────────────────────                          │
│  • 标识一次 Agent 执行                                            │
│  • 与 trace_id 一对一或一对多（多轮对话）                         │
│  • 格式：run_ + 16位十六进制                                     │
│                                                                  │
│  span（跨度）：                                                   │
│  ─────────────────────────────────────                          │
│  • Trace 中的一个操作单元                                         │
│  • 包含：开始时间、结束时间、属性、事件                           │
│  • 形成树形结构（父子关系）                                       │
│                                                                  │
│  关系图：                                                         │
│                                                                  │
│  trace_id: tr_abc123 (一次请求)                                  │
│  │                                                              │
│  ├── span: intent_detection (意图识别)                          │
│  │   └── span: llm_call (LLM 调用)                              │
│  │                                                              │
│  └── run_id: run_xyz789 (Agent 执行)                            │
│      │                                                          │
│      ├── span: rag_retrieval (检索)                             │
│      │   ├── span: milvus_query (向量查询)                      │
│      │   └── span: rerank (重排序)                              │
│      │                                                              │
│      └── span: llm_call (生成答案)                               │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

## 2. 四大支柱：日志、追踪、指标、审计

### 2.1 日志（Logs）

**定义**：离散的事件记录，记录"发生了什么"

**特点**：
- 文本形式，包含丰富上下文
- 有时间戳
- 可以包含任意结构化数据
- 量大，需要日志收集系统

**日志级别**：
```
DEBUG < INFO < WARNING < ERROR < CRITICAL

DEBUG：开发调试信息（生产环境通常关闭）
INFO：正常业务流程
WARNING：潜在问题（如重试）
ERROR：错误（如异常捕获）
CRITICAL：严重错误（如服务不可用）
```

**传统日志 vs 结构化日志**：

```python
# 传统日志
logger.info("意图识别完成，类型=analytics，置信度=0.92")

# 结构化日志
{
    "timestamp": "2024-01-15T14:30:00.000Z",
    "level": "INFO",
    "trace_id": "tr_abc123",
    "event": "intent_detected",
    "message": "意图识别完成",
    "extra": {
        "intent_type": "analytics",
        "confidence": 0.92,
        "duration_ms": 45
    }
}
```

**为什么需要结构化日志？**

| 传统日志 | 结构化日志 |
|----------|-----------|
| "意图识别完成" | 可搜索：`event = "intent_detected"` |
| "类型=analytics" | 可过滤：`intent_type = "analytics"` |
| "耗时45ms" | 可聚合：`avg(duration_ms)` |
| 难以和其他系统集成 | JSON 格式，易于解析 |

### 2.2 追踪（Traces）

**定义**：请求在分布式系统中的完整路径

**核心概念**：
- **Trace**：一次请求的完整路径
- **Span**：Trace 中的一个操作
- **Parent-Child**：Span 之间的调用关系

```
┌─────────────────────────────────────────────────────────────────┐
│                    Trace 示例：用户查询本月发电量                   │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  trace_id: tr_20240115_abc123                                    │
│                                                                  │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │ root span: HTTP /api/v1/chat                             │  │
│  │                                                           │  │
│  │   ┌────────────────────────────────────────────────────┐ │  │
│  │   │ span: intent_detection (45ms)                     │ │  │
│  │   │                                                     │ │  │
│  │   │   ┌────────────────────────────────────────────┐   │ │  │
│  │   │   │ span: llm_call (40ms)                    │   │ │  │
│  │   │   │ prompt_tokens: 120, completion_tokens: 35 │   │ │  │
│  │   │   └────────────────────────────────────────────┘   │ │  │
│  │   └────────────────────────────────────────────────────┘ │  │
│  │                                                           │  │
│  │   ┌────────────────────────────────────────────────────┐ │  │
│  │   │ span: rag_agent (620ms)                           │ │  │
│  │   │                                                     │ │  │
│  │   │   ┌────────────────────────────────────────────┐   │ │  │
│  │   │   │ span: hybrid_search (80ms)                │   │ │  │
│  │   │   │   ├─ dense_retrieval: 50ms               │   │ │  │
│  │   │   │   └─ sparse_retrieval: 30ms              │   │ │  │
│  │   │   └────────────────────────────────────────────┘   │ │  │
│  │   │                                                     │ │  │
│  │   │   ┌────────────────────────────────────────────┐   │ │  │
│  │   │   │ span: rerank (25ms)                       │   │ │  │
│  │   │   │ top_k: 10 → 5                             │   │ │  │
│  │   │   └────────────────────────────────────────────┘   │ │  │
│  │   │                                                     │ │  │
│  │   │   ┌────────────────────────────────────────────┐   │ │  │
│  │   │   │ span: llm_call (500ms)                    │   │ │  │
│  │   │   │ prompt_tokens: 800, completion_tokens: 200│   │ │  │
│  │   │   └────────────────────────────────────────────┘   │ │  │
│  │   └────────────────────────────────────────────────────┘ │  │
│  └──────────────────────────────────────────────────────────┘  │
│                                                                  │
│  总耗时：665ms                                                    │
│  LLM Token 消耗：prompt=920, completion=235                     │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

**追踪的作用**：

1. **性能分析**：哪个环节耗时最长？
2. **错误定位**：错误发生在哪个 span？
3. **依赖分析**：一次请求调用了哪些服务？

### 2.3 指标（Metrics）

**定义**：数值型的测量值，通常随时间聚合

**三种核心指标类型**：

```
┌─────────────────────────────────────────────────────────────────┐
│                    三大指标类型                                    │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  1. Counter（计数器）                                            │
│  ─────────────────────────────────────                          │
│  特点：只能递增，不能减少                                         │
│  用途：请求数、错误数、Token 消耗                                 │
│                                                                  │
│  示例：                                                           │
│  requests_total{endpoint="/chat"} = 12345                        │
│  errors_total{type="timeout"} = 23                               │
│                                                                  │
│  ┌─────────────────────────────────────────────┐               │
│  │  ^                                        │               │
│  │  │         ╱                               │               │
│  │  │       ╱                                 │               │
│  │  │     ╱                                   │               │
│  │  │   ╱                                     │               │
│  │  │ ╱                                       │               │
│  │  └──────────────────────────────────────► │               │
│  └─────────────────────────────────────────────┘               │
│  时间 →  值只能增加                                         │
│                                                                  │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  2. Gauge（仪表）                                                │
│  ─────────────────────────────────────                          │
│  特点：可增可减                                                   │
│  用途：当前连接数、队列长度、CPU 使用率                           │
│                                                                  │
│  示例：                                                           │
│  active_connections = 42                                         │
│  queue_length{queue="high"} = 15                                 │
│                                                                  │
│  ┌─────────────────────────────────────────────┐               │
│  │  │    ╭───╮                               │               │
│  │  │ ───╯     ╰───╮                         │               │
│  │  │               ╰─────                     │               │
│  │  └──────────────────────────────────────► │               │
│  └─────────────────────────────────────────────┘               │
│  时间 →  值可以波动                                         │
│                                                                  │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  3. Histogram（直方图）                                          │
│  ─────────────────────────────────────                          │
│  特点：记录分布，统计百分位数                                     │
│  用途：延迟分布、响应大小                                        │
│                                                                  │
│  示例：                                                           │
│  request_duration_seconds_bucket{le="0.1"} = 1000               │
│  request_duration_seconds_bucket{le="0.5"} = 5000               │
│  request_duration_seconds_bucket{le="1.0"} = 8000               │
│                                                                  │
│  ┌─────────────────────────────────────────────┐               │
│  │                              ████           │               │
│  │                          ████████████       │               │
│  │                      ████████████████████   │               │
│  │  ████                                   ████│               │
│  │───────────────────────────────────────────────│               │
│  │  0ms   100ms  200ms  500ms  1s     延迟     │               │
│  └─────────────────────────────────────────────┘               │
│                                                                  │
│  可计算：P50(中位数)、P90、P99                                    │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

**Agent 平台关键指标**：

| 指标类型 | 指标名称 | 说明 |
|----------|----------|------|
| Counter | `requests_total` | 总请求数 |
| Counter | `llm_tokens_total` | Token 消耗 |
| Counter | `errors_total` | 错误数 |
| Gauge | `active_runs` | 活跃执行数 |
| Histogram | `request_duration_seconds` | 请求延迟 |
| Histogram | `llm_latency_seconds` | LLM 调用延迟 |

### 2.4 审计（Audit）

**定义**：记录安全和合规相关的事件

**审计 vs 普通日志**：

| 维度 | 普通日志 | 审计日志 |
|------|----------|----------|
| **目的** | 调试、监控 | 合规、安全 |
| **内容** | 技术细节 | 业务操作 |
| **保存时长** | 短期（7-30天） | 长期（1-5年） |
| **访问权限** | 开发运维 | 安全合规团队 |
| **格式** | 灵活 | 标准化 |
| **法律效力** | 无 | 可作为证据 |

**Agent 平台需要审计的事件**：

```
┌─────────────────────────────────────────────────────────────────┐
│                    审计事件类型                                    │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  1. Agent 执行事件                                                │
│  ─────────────────────────────────────                          │
│  • AGENT_REQUEST：收到用户请求                                    │
│  • AGENT_RESPONSE：返回响应                                       │
│  • AGENT_ERROR：执行错误                                         │
│                                                                  │
│  2. 工具调用事件                                                  │
│  ─────────────────────────────────────                          │
│  • TOOL_INVOCATION：工具被调用                                    │
│  • TOOL_RESULT：工具返回结果                                      │
│  • TOOL_ERROR：工具执行错误                                       │
│                                                                  │
│  3. 数据访问事件                                                  │
│  ─────────────────────────────────────                          │
│  • DATA_RETRIEVAL：文档检索（RAG）                               │
│  • DATA_QUERY：SQL 查询                                          │
│  • DATA_EXPORT：数据导出                                         │
│                                                                  │
│  4. 高风险操作                                                    │
│  ─────────────────────────────────────                          │
│  • REVIEW_REQUEST：人工复核请求                                   │
│  • REVIEW_APPROVE：复核通过                                       │
│  • REVIEW_REJECT：复核拒绝                                        │
│                                                                  │
│  5. 安全事件                                                      │
│  ─────────────────────────────────────                          │
│  • AUTH_SUCCESS：认证成功                                         │
│  • AUTH_FAILURE：认证失败                                         │
│  • PERMISSION_DENIED：权限拒绝                                   │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

**风险等级**：

```
RiskLevel.LOW      → 普通操作，如查询知识库
RiskLevel.MEDIUM   → 需要注意，如 SQL 查询
RiskLevel.HIGH     → 需要复核，如合同审批
RiskLevel.CRITICAL → 极高风险，如敏感数据导出
```

### 3.2 上下文传递机制

**问题**：如何在异步、多线程环境中传递 trace_id？

**解决方案**：Python contextvars

```
┌─────────────────────────────────────────────────────────────────┐
│                    contextvars 工作原理                            │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  问题场景：                                                       │
│  ─────────────────────────────────────                          │
│  async def handle_request():                                     │
│      trace_id = "tr_abc123"  # 设置                             │
│      await some_async_function()  # 调用另一个协程               │
│                                                                  │
│  async def some_async_function():                                │
│      print(trace_id)  # 这里能访问到吗？                        │
│                                                                  │
│  ThreadLocal 的问题：                                             │
│  ─────────────────────────────────────                          │
│  • 协程切换时 ThreadLocal 仍然绑定到线程                         │
│  • 但协程可能切换到其他线程                                       │
│  • 导致上下文丢失                                                 │
│                                                                  │
│  contextvars 的优势：                                            │
│  ─────────────────────────────────────                          │
│  • 每个协程有独立的上下文                                         │
│  • 在 await 点自动传递                                           │
│  • 协程切换到不同线程也能保持                                    │
│                                                                  │
```

### 4.2 上下文管理（context.py）

**核心要点**：
1. 使用 `contextvars` 实现异步安全的上下文传递
2. `trace_id` 和 `run_id` 自动生成
3. 提供上下文管理器 `TraceContext`

```python
"""
关键代码解析：context.py

Q1: 为什么要用 contextvars 而不是 threading.local？

A1:
threading.local 在协程环境下有问题：
- async/await 切换时，同一线程可能执行不同协程
- 协程A设置的值可能被协程B读取到

contextvars 为每个协程维护独立的上下文：
- await 会自动传递上下文
- 不同协程互不影响

Q2: 如何生成 trace_id？

A2:
使用 UUID，但只取前16位：

def generate_trace_id() -> str:
    return f"tr_{uuid.uuid4().hex[:16]}"

这样：
- 保证唯一性（UUID 的前16位已经足够）
- 长度适中，便于阅读

Q3: TraceContext 的作用是什么？

A3:
上下文管理器，确保资源正确清理：

async with TraceContext() as ctx:
    # 自动设置 trace_id, run_id
    logger.info("Hello")
    await process()
# 自动清除上下文，避免内存泄漏

为什么要清除？
- 上下文变量会占用内存
- 长期累积可能导致内存泄漏
- 请求结束时清理是最佳实践
"""

from contextvars import ContextVar

# 定义上下文变量
_trace_id_var: ContextVar[str | None] = ContextVar(
    "trace_id",
    default=None
)

# 使用示例
_trace_id_var.set("tr_abc123")

async def child():
    # 自动继承 trace_id
    print(_trace_id_var.get())  # "tr_abc123"

async def main():
    trace_id, run_id = set_trace_context(
        trace_id="tr_abc123",
        user_id="user_001"
    )
    await child()

# 或者使用上下文管理器
async with TraceContext() as ctx:
    logger.info("操作")
    await process()
# 自动清理
```

### 4.4 分布式追踪（trace.py）

**核心要点**：
1. Trace 由多个 Span 组成
2. Span 之间有父子关系
3. 提供装饰器自动管理 Span 生命周期

```python
"""
关键代码解析：trace.py

Q1: 什么是 Span？为什么需要 Span？

A1:
Span 是追踪的基本单元：

Trace: 用户请求
├── Span: HTTP 入口
│   ├── Span: 意图识别
│   │   └── Span: LLM 调用
│   └── Span: RAG 检索
│       ├── Span: Milvus 查询
│       └── Span: 重排序

每个 Span 记录：
- 开始时间、结束时间
- 耗时
- 属性（如 prompt_tokens）
- 事件（如"查询成功"）

为什么需要？
- 知道哪个环节慢
- 知道调用关系
- 知道错误位置

Q2: 如何自动管理 Span 生命周期？

A2:
使用装饰器：

@traced(span_name="rag_retrieval")
async def retrieve(query: str):
    # 自动创建 Span
    # 自动记录开始时间
    # 自动记录结束时间
    # 自动计算耗时
    return await do_retrieval(query)

原理：
@traced
def func():
    ↓ 编译器转换为 ↓

def func():
    span = tracer.start_span("func")
    try:
        return original_func()
    except:
        span.end(status=SpanStatus.ERROR)
        raise
    span.end(status=SpanStatus.OK)

Q3: parent_span_id 的作用是什么？

A3:
构建 Span 树：

Span A (root)
├── Span B (parent=A)
│   └── Span D (parent=B)
└── Span C (parent=A)

通过 parent_span_id 形成树形结构：
- Span B.parent_span_id = A.span_id
- Span D.parent_span_id = B.span_id

这使得：
1. 可以还原完整调用链
2. 可以计算父子耗时
3. 可以在 UI 上展示为树形图
"""

# Span 树示例
span_tree = {
    "trace_id": "tr_abc123",
    "spans": [
        {
            "span_id": "sp_001",
            "parent_span_id": None,  # 根节点
            "name": "http_request",
            "children": ["sp_002", "sp_005"]
        },
        {
            "span_id": "sp_002",
            "parent_span_id": "sp_001",
            "name": "intent_detection",
            "children": ["sp_003"]
        },
        {
            "span_id": "sp_003",
            "parent_span_id": "sp_002",
            "name": "llm_call",
            "children": []
        }
    ]
}
```

### 4.6 Prometheus 指标（metrics.py）

**核心要点**：
1. Counter、Gauge、Histogram 三种类型
2. 支持标签，便于多维度分析
3. Prometheus 格式导出

```python
"""
关键代码解析：metrics.py

Q1: Counter、Gauge、Histogram 的区别和使用场景？

A1:
Counter（只能递增）：
    用途：请求数、错误数、Token消耗
    示例：
        metrics.increment("requests_total")
        metrics.increment("errors_total")
        metrics.increment("tokens_total", value=100)

Gauge（可增可减）：
    用途：当前值，如连接数、队列长度
    示例：
        metrics.gauge("active_connections", 100)
        metrics.gauge("queue_length", 50)  # 可以减少

Histogram（记录分布）：
    用途：延迟、大小分布
    示例：
        metrics.observe("request_duration", 0.125)  # 秒
        metrics.observe("response_size", 1024)  # 字节

    可以计算：
    - P50（中位数）
    - P90（90% 请求的耗时）
    - P99（99% 请求的耗时）

Q2: 为什么需要标签（tags/labels）？

A2:
没有标签：
    requests_total = 10000

有标签：
    requests_total{endpoint="/chat"} = 5000
    requests_total{endpoint="/search"} = 3000
    requests_total{endpoint="/admin"} = 2000

好处：
1. 可过滤：只看 /chat 的请求
2. 可聚合：计算各端点的请求占比
3. 可分析：按端点分析性能

Q3: Histogram 的 buckets 是什么？

A3:
buckets 定义了统计区间：

request_duration_seconds_bucket{le="0.1"} = 100    # 100个请求 < 100ms
request_duration_seconds_bucket{le="0.5"} = 500    # 500个请求 < 500ms
request_duration_seconds_bucket{le="1.0"} = 800    # 800个请求 < 1s
request_duration_seconds_bucket{le="+Inf"} = 1000  # 总共1000个请求

计算百分位：
- P50 = 第一个达到 50% 的 bucket 上限
- P90 = 第一个达到 90% 的 bucket 上限

常用 buckets 配置：
# HTTP 延迟
(0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1.0, 2.5, 5.0, 10.0)

# LLM 延迟（可能很慢）
(0.1, 0.5, 1.0, 2.5, 5.0, 10.0, 30.0, 60.0)
"""

# 指标导出示例（Prometheus 格式）
"""
# HELP requests_total Total HTTP requests
# TYPE requests_total counter
requests_total{endpoint="/chat",method="POST",status="200"} 5000
requests_total{endpoint="/search",method="POST",status="200"} 3000
requests_total{endpoint="/chat",method="POST",status="500"} 10

# HELP request_duration_seconds Request duration in seconds
# TYPE request_duration_seconds histogram
request_duration_seconds_bucket{endpoint="/chat",le="0.1"} 4500
request_duration_seconds_bucket{endpoint="/chat",le="0.5"} 4900
request_duration_seconds_bucket{endpoint="/chat",le="1.0"} 4980
request_duration_seconds_bucket{endpoint="/chat",le="+Inf"} 5000
request_duration_seconds_sum{endpoint="/chat"} 250.5
request_duration_seconds_count{endpoint="/chat"} 5000
"""
```

### 5.3 LLM 调用埋点

```python
# LLM 调用的完整可观测性

async def call_llm(prompt: str, model: str = "gpt-4"):
    from core.observability import get_tracer
    tracer = get_tracer()

    # 创建 Span
    span = tracer.start_span(
        "llm_call",
        attributes={
            "model": model,
            "prompt_length": len(prompt),
        }
    )

    try:
        # 记录审计
        audit_log.log_tool_invocation(
            tool_name=f"llm.{model}",
            parameters={"prompt_length": len(prompt)},
        )

        # 计时
        start = time.time()
        response = await openai.ChatCompletion.create(
            model=model,
            messages=[{"role": "user", "content": prompt}]
        )
        duration_ms = (time.time() - start) * 1000

        # 提取 token 使用量
        usage = response.usage
        prompt_tokens = usage.prompt_tokens
        completion_tokens = usage.completion_tokens

        # 添加 Span 事件
        tracer.add_span_event(
            span,
            name="llm_response",
            attributes={
                "completion_tokens": completion_tokens,
                "total_tokens": usage.total_tokens,
            }
        )

        # 记录指标
        metrics.record_llm_call(
            model=model,
            provider="openai",
            success=True,
            prompt_tokens=prompt_tokens,
            completion_tokens=completion_tokens,
            duration_ms=duration_ms,
        )

        # 记录审计
        audit_log.log_tool_result(
            tool_name=f"llm.{model}",
            result_summary=f"生成 {completion_tokens} tokens",
            duration_ms=duration_ms,
        )

        tracer.end_span(span, SpanStatus.OK)
        return response

    except Exception as e:
        duration_ms = (time.time() - start) * 1000

        # 错误处理
        tracer.end_span(span, SpanStatus.ERROR, e)

        metrics.record_llm_call(
            model=model,
            provider="openai",
            success=False,
            duration_ms=duration_ms,
        )

        audit_log.log_tool_result(
            tool_name=f"llm.{model}",
            success=False,
            duration_ms=duration_ms,
        )

        raise
```

## 6. 面试要点：高频面试题解析

### 6.1 概念类问题

**Q1: 什么是可观测性？和监控有什么区别？**

```
参考答案：

监控（Monitoring）：
- 回答"系统是否健康"
- 关注：CPU、内存、网络等系统指标
- 被动：预设指标，超阈值告警

可观测性（Observability）：
- 回答"为什么系统这样表现"
- 关注：请求链路、业务语义、用户行为
- 主动：任意问题都可以定位

区别：
┌──────────────────┬──────────────────┐
│     监控         │    可观测性       │
├──────────────────┼──────────────────┤
│ 问：系统健康吗？  │ 问：为什么这样？  │
```

**Q2: 解释 trace_id、run_id、span 的区别和联系？**

```
参考答案：

trace_id：
- 一次完整请求的标识
- 从入口生成，沿整个链路传递
- 用于关联所有相关日志和追踪

run_id：
- 标识一次 Agent 执行
- 与 trace_id 一对一（单轮）或一对多（多轮）
- 用于关联同一 Agent 的多次调用

span：
- Trace 中的操作单元
- 有开始时间、结束时间、属性
- 形成树形结构（父子关系）

关系：
- 1 trace = N spans（树形）
- 1 trace = 1~N runs（多轮对话）
- span 包含 run_id，但不等于 run_id
```

**Q3: 为什么要用结构化日志？**

```
参考答案：

传统日志的问题：
1. 难以搜索："意图识别完成" - 怎么搜？
2. 难以过滤：只知道 ERROR，不知道哪个 trace_id
3. 难以聚合：无法计算平均耗时
4. 难以扩展：加字段要改代码

结构化日志的优势：
1. 字段搜索：event = "intent_detected"
2. 字段过滤：trace_id = "tr_abc123"
3. 字段聚合：avg(duration_ms)
4. 易于扩展：加字段不影响旧代码

示例对比：
# 传统
logger.info("意图识别完成，类型=analytics，置信度=0.92，耗时=45ms")

# 结构化
{
    "event": "intent_detected",
    "intent_type": "analytics",
    "confidence": 0.92,
    "duration_ms": 45
}
```

**Q4: 如何设计一个高可观测性的 Agent 系统？**

```
四大支柱：
```

**Q5: 如何实现跨服务追踪？**

```
参考答案：

方案1：OpenTelemetry
- 标准化的跨服务追踪方案
- 自动注入 trace_id 到 HTTP header
- 支持多种语言和框架

方案2：手动传递
- 请求入口生成 trace_id
- 通过 HTTP header / RPC metadata 传递
- 每个服务解析并继续传递

实现要点：
1. trace_id 必须从入口透传到所有调用
2. 异步场景用 contextvars
3. HTTP 场景用 W3C Trace Context 标准
4. 日志和追踪用同一个 trace_id 关联
```

### 6.3 实践类问题

**Q6: Python 中如何实现异步上下文传递？**

```
参考答案：

使用 contextvars（Python 3.7+）：

from contextvars import ContextVar

trace_id: ContextVar[str] = ContextVar("trace_id", default=None)

# 设置
trace_id.set("tr_abc123")

# 获取
print(trace_id.get())  # "tr_abc123"

# 异步传递
async def child():
    # 自动继承 trace_id
    print(trace_id.get())  # "tr_abc123"

async def parent():
    trace_id.set("tr_abc123")
    await child()

为什么不用 threading.local？
- 协程切换时可能丢失上下文
- 同一线程执行多个协程会冲突

contextvars 的优势：
- 每个协程独立上下文
- await 自动传递上下文
- 线程安全 + 协程安全
```

**Q7: 如何评估 RAG 系统的性能？需要哪些指标？**

```
参考答案：

核心指标：

1. 检索质量
   - Hit Rate：正确答案在检索结果中的比例
   - MRR（Mean Reciprocal Rank）：正确答案排名的倒数均值
   - NDCG：考虑排名的评估指标

2. 性能指标
   - 检索延迟：P50、P90、P99
   - Token 消耗：prompt_tokens + completion_tokens
   - 端到端延迟：从问句到回答的总时间

3. 业务指标
   - 用户满意度：回答是否有帮助
   - 澄清率：需要追问的比例
   - 答案引用准确率：引用的文档是否相关

可观测性埋点：
- retrieval_duration_seconds
- retrieval_hit_rate
- retrieved_chunk_count
- llm_token_usage_total
```

### 7.1 OpenTelemetry 集成

```python
"""
生产环境推荐使用 OpenTelemetry

优势：
1. 标准化：供应商无关
2. 生态好：支持 Jaeger、Zipkin、Tempo
3. 自动埋点：FastAPI、Django 自动 instrumentation
4. 采样支持：降低大数据量场景成本

集成示例：
"""

from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor
from opentelemetry.exporter.jaeger.thrift import JaegerExporter
from opentelemetry.instrumentation.fastapi import FastAPIInstrumentor

# 1. 创建 TracerProvider
provider = TracerProvider()

# 2. 配置 Jaeger 导出器
jaeger_exporter = JaegerExporter(
    agent_host_name="jaeger",
    agent_port=6831,
)

# 3. 添加导出处理器
provider.add_span_processor(
    BatchSpanProcessor(jaeger_exporter)
)

# 4. 设置全局 TracerProvider
trace.set_tracer_provider(provider)

# 5. FastAPI 自动埋点
FastAPIInstrumentor.instrument_app(app)
```

### 7.2 采样策略

```python
"""
大数据量场景需要采样

常见策略：
1. 头部采样：固定比例（如 1%）
2. 尾部采样：只采样慢请求或错误
3. 规则采样：按 trace_id 哈希

实现示例：
"""

class SamplingStrategy:
    def should_sample(self, trace_id: str) -> bool:
        raise NotImplementedError


class HeadSampling(SamplingStrategy):
    """头部采样：固定比例"""

    def __init__(self, rate: float = 0.01):
        self.rate = rate

    def should_sample(self, trace_id: str) -> bool:
        # 基于 trace_id 哈希决定
        hash_value = int(trace_id.split("_")[1], 16)
        return (hash_value % 10000) < (self.rate * 10000)


class TailSampling(SamplingStrategy):
    """尾部采样：只采样慢请求或错误"""

    def __init__(self, latency_threshold_ms: int = 1000):
        self.latency_threshold_ms = latency_threshold_ms
        self.pending_traces: dict[str, Span] = {}

    def should_sample(self, trace_id: str, latency_ms: float, has_error: bool) -> bool:
        # 慢请求或错误必采样
        if latency_ms > self.latency_threshold_ms or has_error:
            return True

        # 随机采样一小部分
        return random.random() < 0.001
```
